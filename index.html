Q0.130 秒定位：你是做什么的必背›
面试官原话

先简单介绍一下自己，用一两句话说清你是做什么的。

20 秒答法
「我把业务流程拆成 Agent 能干活、人能管、效果能回查的系统。具体做过两段：一段让研究员从翻十几个数据源，变成看一份每条结论都有出处的报告；一段让销售不用切五个系统，就能查清一个客户的来龙去脉。」
展开讲

定位这句话的公式是「我的能力 + 两段经历各自的变化」，不是「我叫什么、哪个学校、会什么技术」。前者让他在脑子里给你放一个位置，后者只是在念他已经拿在手上的简历。

两段经历各自只给一个变化：从什么变成什么。不给技术栈、不给项目全名——他要问会自己问，你一上来报完，他就没得问了。

三句里的三个词各有落点，被追问时能立刻展开：

说法对应你项目里的什么
能干活工具调用：注册表里挂了能力，模型能真的取数、查客户
人能管高风险动作人工确认：对客消息只出草稿，没有直接发送能力
效果能回查每条结论有依据、每次运行有记录、改一版能跑回归
他可能追什么
  • 「能干活、人能管、能回查，这三句分别指什么？」→ 按上表三行答，每行给一个项目事实，别停在词上。
  • 「你说的『系统』是你搭的，还是团队搭的？」→ 直接切贡献边界：装配和评测里的两块是我做的，框架是团队定的。
Q0.2目标公司三框架待你填›
面试官原话

你为什么来我们公司？你了解我们是做什么的吗？

20 秒答法
「【待你填】三句：① 这家公司靠什么赚钱、钱从谁口袋里出；② 这个行业最痛的是哪一段、AI 正在改哪一段；③ 这个岗位最想证明的一个能力，我用哪段经历接。」
展开讲

这三句是面试前唯一必须查的东西。查完写成三行，念一遍看顺不顺——念着别扭，说明还没真懂，只是抄了官网介绍。

判断标准：

  • 第一句不能是「做 SaaS 的」「做 AI 的」这种。要说清谁付钱、为什么付。
  • 第二句要有取舍：一个行业痛点往往有五六个，你只挑一个，说明你判断过。
  • 第三句必须落到你的具体经历，不能是「我学习能力强」。

这一格我填不了。你对哪家公司有想法，把三句告我，我帮你压到能顺口念的长度。

他可能追什么
  • 「那你觉得我们最该先做哪个场景？」→ 别空口说。用 Q1.2 的七维打分器现场过一遍，边勾边说结论。
  • 「你看过我们的产品吗？」→ 看过就说看过哪一个功能、你觉得它解决的是谁的什么问题；没看过就老实说没深度用过，别编。
Q0.3技术选型口诀：五个词怎么分必背›
面试官原话

这个场景你打算用 Workflow 还是 Agent？为什么？

20 秒答法
「固定流程走 Workflow，固定动作用 Tool，复杂任务才上 Agent，稳定能力沉成 Skill，外部知识走 RAG。够用最简，不够才加复杂度——不是越智能越好，是越可控越好。」
展开讲

五个词的分界不在「难不难」，在谁决定下一步：

词谁决定下一步什么时候用它
Workflow人，写死的步骤和分支都能提前定下来
Tool模型决定调不调，但动作本身是确定的取数、查询、写入这类固定动作
Agent模型自己判断路径不预先确定，要边看边决定
Skill人，作为一段可复用能力被调用一组常用动作 + 提示词 + 约束，反复要用
RAG不涉及决定，只负责喂料模型「不知道」而不是「不会做」

一句话记：流程能定就别交给模型定。每交给模型一步，就多一处不可预测，也多一处要评测的地方。

他可能追什么
  • 「你们项目里哪里用了 Agent，哪里其实不需要？」→ 取数是 Workflow（四项并发、顺序固定、单项 20 秒超时）；只有综合判断那一步才交给模型。
  • 「为什么不用一个大 Agent 全做完？」→ 角色、上下文、工具权限、责任边界分不清；出错时定位不到是哪一段坏的。
  • 「Skill 和 Tool 差在哪？」→ Tool 是原子动作（查一次客户），Skill 是一套做法（怎么查、查完怎么判、什么情况停手）。
Q0.4数字锚点：每个数字都讲得出来历必背›
面试官原话

你刚说六十多个工具，具体是什么？八十多条用例怎么来的？

20 秒答法
「我要求自己每个数字都能说三件事：它是什么、怎么数出来的、为什么是这个数。说不出来历的数字，宁可不写。」
展开讲
数字属于一句话来历
十段投研的上下文装配装配顺序固定十段；第 6 段之后插一句 active symbol，专门消解「这个」指谁
86 条投研评测用例12 个确定性评测器 + 语义评审；其中 8 条是从真实缺陷回填的回归
12 个确定性评测器框架是团队先定的，我接进去 12 个，工具召回和证据存在性这两个是我写的
60+客户经营的工具注册表是全集，按客户已购包筛完才是模型看到的那些
四个客户经营的内置 Agent权限各自配；独立 Run 不自动带历史
24 个开源 PR8 个 AI/Agent 项目，全部已合入主线；修的多数是「不报错但结果错」

为什么数字比形容词有效：评价会被怀疑，数字可以被核对。但前提是每个数字你都讲得出来历——一个说不清来历的数字，会把整场面试的可信度拉低。

他可能追什么
  • 「60+ 是全部还是给模型看的？」→ 全集在注册表里，按已购包筛选后才是模型实际能看到的。
  • 「86 条够吗？」→ 不够，而且我知道不够。它只覆盖「发生过、且能被机械断言」的缺陷；只能靠语义判断的进人工评审。
  • 「24 个 PR 都是你写的？」→ 是我提的，全部已合入。修的是具体缺陷，不是改错别字。
Q0.5每段经历一句话业务逻辑必背›
面试官原话

这两段经历，各自解决什么问题？

20 秒答法
「投研那段：研究员要在十几个数据源之间来回翻，翻完还担心数字对不上——我把它做成取数、综合、出报告一条线，每条结论能回查到依据。客户经营那段：销售要查一个客户的来龙去脉得切五个系统——我把它封成六十多个工具，一句话就能查到，而且发给客户的东西只出草稿，必须人点确认。」
展开讲

格式固定三段：痛点（多痛）→ 我做的（一句话）→ 变成什么。

关键是两段不要讲成同一件事。第一段的核心是可信（数字对不对、有没有依据），第二段的核心是可控（会不会越权、会不会发错）。

投研 Agent客户经营 Agent
用户研究员销售
痛点数据散、对不上账、翻得慢信息散在五个系统、查一次要半天
核心风险答案不准，可以返工对外发错话，不可逆
一句话价值从翻数据变成看结论，且结论有出处从切系统变成一句话问，且动作要人确认
他可能追什么
  • 「哪段更难？」→ 客户经营。投研错了是报告不准，能返工；客户经营错了是对外发了错话，代价不可逆——所以它必须在工具层就没有「直接发」这个能力。
  • 「两段有共享的东西吗？」→ 有方法复用，没有共享数据库和代码。别硬说成一个系统。
Q0.6场景题走位 5 步（紧张时用这个）必背›
面试官原话

给你一个场景，你怎么设计？

20 秒答法
「五步：先问两个澄清问题；再定骨架——业务对象、数据、AI 能力、编排、人工与权限、闭环；然后挑最小可评测的场景做 POC；接着画安全阀；最后用 ROI 收尾。」
展开讲

这五步是 12 步的压缩版。时间紧、或者对方只是随口一问，用这五步就够；他要是往下追，再展开成 12 步（板块 1）。

顺序不能换，三条理由：

  • 先问再定：不问就出方案，等于假设了一堆没验证的前提。
  • 先小再大：一上来讲全量架构，他没法判断你说得对不对，只能判断你会不会画图。
  • 先安全阀再谈价值：业务方最怕的是「AI 捅娄子」，不是「AI 不够聪明」。先给兜底，他才听得进价值。
他可能追什么
  • 「最小的 POC 怎么挑？」→ 数据可及、流程确定、价值直接、结果能评测，四条同时满足的那个。缺一条就换个场景。
  • 「ROI 怎么算？」→ 拿现在的人工基线算：几个人、一天几小时、一年错几次。算不出来就说明还没到能做的时候。
Q0.7高频十问：20 秒答法（前 5 必背）必背›
面试官原话

随口问的技术题，你怎么在 20 秒内给出判断？

20 秒答法
「一、Agent 和 Chatbot 差在哪：Chatbot 回答，Agent 执行——它会调工具、改状态。二、为什么不用一个大 Agent 全做完：角色、上下文、权限、责任要拆开，否则出错定位不到。三、数据不能出域怎么办：私有化部署、权限在服务层过滤、只把脱敏候选给模型。四、怎么防幻觉：事实靠工具读、结构靠 Schema 卡、结论要引用、写操作要人确认。五、效果怎么证明：一组固定用例加确定性断言，改一版跑一遍，分数可比。」
展开讲

20 秒答法的标准是三句：第一句给判断，第二句给理由，第三句给代价。三句之内没说完，说明自己还没想清楚。

问题判断（第一句）理由 / 代价（第二、三句）
Agent vs ChatbotChatbot 回答，Agent 执行差别在有没有副作用：调工具会改状态，改错了要能回滚
为什么不全塞一个 Agent拆开更好观察、更好兜底代价是编排复杂；收益是出错能定位到具体一段
数据不能出域私有化 + 服务层过滤权限代价是模型能力受限；兜底是只给脱敏候选，不给原始表
防幻觉四道闸：工具读事实、Schema 卡结构、引用校验、人工确认四道都过也挡不住语义层面的错，那部分只能靠评测
证明效果固定用例 + 确定性断言 + 版本化数据集分数只有同一套用例之间才能比，换用例等于换尺子
他可能追什么
  • 任何一条追问，都往你项目里的具体数字上落，别回抽象原则。比如「防幻觉怎么落地」→ 答「某项取数失败就标不可用，不能静默删掉这个维度」。
Q0.8反问三问待你填›
面试官原话

你有什么想问我的吗？

20 秒答法
「【待你填】三个反问，每个都要能问出『这家公司怎么判断一件事做成了』。」
展开讲

反问不是走过场，是最后一次证明你在想业务。三类可问：

  • 这个岗位现在最头疼的一件事是什么？（问出真实痛点，也能判断这活好不好干）
  • 这类项目做到什么程度算成功，谁来验收？（问出组织对 AI 的真实预期）
  • 团队现在卡在哪：是数据、是模型，还是没人愿意用？（问出他们踩过的坑）

不要问：加班多不多、转正率多少、用什么技术栈。前两个让他觉得你只关心待遇，第三个让他觉得你只关心工具。

这三问我填不了——得你自己挑，而且要根据当场聊的内容调整。聊完你觉得他关心什么，就往那个方向反问他。

他可能追什么
  • 无追问。但你的反问会被他记住，比你的答案记得久。
Q0.9金句：选 3 句背下来›
面试官原话

（隐含）这个人有没有自己的判断？

20 秒答法
「我常说的是这一句：我设计的每一步都有数据来源和人工节点——这是证据链管理，不是模型表演。」
展开讲

候选六句，挑三句，每句都要能带出你项目的具体事实，否则就是背别人的话：

  1. 我设计的每一步都有数据来源和人工节点——这是证据链管理，不是模型表演。挂在：投研的每条结论可回查
  2. AI 负责发现和整理证据，专家负责判断，系统负责留痕，经验负责沉淀。挂在：客户经营的三分摘要（事实/推断/缺失）
  3. POC 我只承诺能验证的三件事：数据进不进得来、效果压不压得住、用户认不认可。挂在：你怎么定验收线
  4. 生成者不能自证合格。挂在：为什么要有确定性评测，不能只靠模型自评
  5. 召回或知识失败不能静默——没有数据要说没有，不能说「未提及」。挂在：某项取数失败降级成「不可用」
  6. 一条真 bug 的终点不是「修好了」，是「变成一条能自动重跑的用例」。挂在：时间粒度那条回归用例

挑选标准：能被追问三层还不塌的才留。第 5、6 句最硬，因为它们背后各有一个真实事故。

他可能追什么
  • 「这句是你自己想的还是看来的？」→ 老实说「从某次事故里总结的」，然后把那次事故讲一遍。这比装作原创强得多。

场景题 12 步

面试官甩一个陌生场景过来时，按这个走，不现场现想。顺序：先问 → 再判断值不值得做 → 才走 12 步。 · 19 张

Q1.0开场 20 秒：先问什么（出口 2 问）必做›
面试官原话

假如我们要做一个 X，你怎么设计？（他没给你任何背景信息）

20 秒答法
「动手前我想先确认两件事：这个场景最怕的风险是什么——是漏报还是误报，做错了代价多大；数据现在在哪、电子化了吗、谁有权限。这两件不同，方案会完全不一样。」
展开讲

这两问是区分「解决方案型」和「只会写代码」的关键信号。不问就直接讲架构，等于替对方假设了一堆没验证的前提。

如果他已经给了信息，别重复问，改成复述确认：

「所以我理解要解决的是……，成功标准是……，对吗？」

复述比追问更显专业——它证明你听懂了，而不是只会套模板。

注意：出口只问 2 个。下面那张「九问」是心里过一遍的清单，不是要你连着问九个。真问九个，面试官会觉得你在拖时间。

他可能追什么
  • 「如果我说我也不知道呢？」→ 按最坏情况假设往下走，并且把假设说出来：「那我按误报代价高来设计，宁可少报不可错报；如果实际相反，这一层要反过来。」
  • 「你为什么不先问预算？」→ 预算决定做多大，风险决定能不能做。顺序上先确认能不能做，再谈做多大。
Q1.1需求访谈九问（过脑，不全问）›
他在测什么

（心里过一遍）这九个问题里，哪些是真瓶颈、哪些只是他嘴上说的？

出口只有 2 问（见上一张），这九条是心里过一遍的清单。每条都带一列「问出来之后你打算干什么」——不加这一列，问了等于白问。

第一组 · 痛找出真正的瓶颈位置
1. 现在怎么解决的？哪一步最耗时、最易错？
为什么问：人说的「慢」常常不是真瓶颈，他只是在描述最烦的那一步。
问出来之后：把 AI 放在最耗时那一步，不是放在最显眼那一步。
2. 出问题最严重的后果是什么？
为什么问：定风险等级，决定要不要人工兜底。
问出来之后：后果不可逆的（对外发送、写生产库、付款），一律加人工确认，不给直接执行能力。
3. 谁在用？一天几次？高峰什么样？
为什么问：定并发和响应要求。
问出来之后：一天三次和一分钟三十次，是两套完全不同的架构。
第二组 · 数决定 POC 能不能做
4. 数据现在在哪？格式统一吗？谁有权限？
为什么问：这是 POC 能不能做的前提，比模型能力重要得多。
问出来之后：如果散在多个系统、口径不统一，第一步是拉通数据，不是做模型。
5. 什么算「做好了」？有没有心里的验收线？
为什么问：没有验收线，做完了也没人说好，项目会一直拖着验收不了。
问出来之后：把验收线写成一个能数的指标。写不进指标，说明这事还没想清。
6. 之前试过什么方案？为什么没成？
为什么问：避免重复踩坑，也避免无意中否定别人的工作。
问出来之后：失败分三种——数据不行、效果不行、没人用。三种对应三种完全不同的改法。
第三组 · 界收敛范围，别做太大
7. 预算、时间、人力什么量级？
为什么问：决定做到 POC 还是做到生产。
问出来之后：只够 POC 就别承诺上线，承诺了就是给自己挖坑。
8. 半年内需求会变吗？哪些会变？
为什么问：决定哪些要留扩展点、哪些可以写死。
问出来之后：会变的做成配置，不会变的写死。全都配置化是最常见的过度设计。
9. 如果只做一个功能先上线，你选哪个？
为什么问：逼出 MVP，同时验证他心里的优先级。
问出来之后：他选的那个，通常就是最痛的那个——和你判断的对一对，不一致就以他的为准。
如果他答「不知道」怎么办

别停在原地追问。直接声明假设往下走：

「那我按最坏情况假设，并写进方案里：假设数据散在三个系统、没有统一口径。如果实际比这好，方案只减不加。」

这句话的作用是：让他知道你清楚自己在假设，而不是把假设当事实。

Q1.2AI 场景值不值得做（七维打分器）›
他在测什么

你觉得这个场景适合用 AI 吗？该用 Agent 吗？

别给态度，给判断依据。下面七个维度，现场在心里勾一遍，十秒就有结论方向。

频率多久触发一次
流程有明确 SOP 吗
数据数据可及吗
结果输出能评测吗
工具有系统或接口可接吗
风险做错代价多大（反过来填）
ROI价值可量化吗
勾完七项，这里出结论。
三条否决线（原模板没说，我补的）
  1. 数据拿不到、短期也补不上 → 不做。模型不能凭空造事实，硬做出来只会编。
  2. 错了不可逆，且没人愿意做复核 → 不做，或者只做「建议」不做「执行」。
  3. 没有验收标准，谁也说不出什么叫做好 → 不做。做完没人认，等于白做一年。

能主动说出「这里不该用 Agent」，比硬答一套架构加分得多——它证明你知道边界在哪。

示范：用两个真实项目过一遍这七维打分不是空表
维度投研 Agent客户经营 Agent
频率高 · 每天多次研究高 · 销售每天查客户
流程高 · 十段固定装配、四步取数中 · 查客户没有固定路径
数据高 · 行情、财报有接口中 · 散在多个系统，要先封成工具
结果高 · 86 条用例可判定中 · 对客话术的好坏靠人判断
工具高 · 20 项能力注册表高 · 60+ 工具
风险中 · 报告错了能返工低 · 对外发错不可逆
ROI高 · 研究耗时明显下降中 · 省的是切系统的时间

结论：两个都能做，但客户经营在「风险」这一项上是不及格的——所以它真实的做法是工具层根本不给直接发送能力，只出草稿，必须人点确认。打分结果直接决定了架构，这才是打分器的用处。

Q1.3第①步 · 业务背景（60 秒）›
面试官原话

先说这个业务是干什么的。

20 秒答法
「一句话：客户是谁、他现在怎么做这件事、为什么要改。三样缺一样，后面全是猜。」
展开讲

业务背景只讲一分钟，但必须有「谁」和「为什么是现在」。没有「为什么现在」的需求，通常是伪需求——只是有人觉得该做 AI 了。

三要素的作用不同：

  • 客户是谁 → 决定后面所有的验收标准（谁说了算）
  • 现在怎么做 → 决定 AI 要插在哪一步，也决定上线后怎么对比效果
  • 为什么现在改 → 决定这事的紧迫度；说不出紧迫度的，通常做一半就停
他可能追什么
  • 「这业务你熟吗？」→ 老实说边界，然后说我怎么补：找一线的人聊，不找管理层。管理层讲的是应该怎么干，一线讲的是实际怎么干。
  • 「为什么要现在改，明年不行吗？」→ 从成本或风险的角度答：人力涨了、错误代价变高了、或者竞争对手已经做了。别答「AI 是大趋势」。
Q1.4第②步 · 用户与角色（执行者 / 确认者 / 维护者）›
面试官原话

这东西谁用？

20 秒答法
「使用者、确认者、维护者要分开说。使用者天天用但不管对错；确认者偶尔用但要对结果签字；维护者不看界面，只看日志。」
展开讲

三者混成一个「用户」，做出来一定有一方不满意。他们的差异：

角色关心什么界面上要给他什么
使用者（执行）快、少填、别让我学新东西默认值、一键采纳、明显的人工修正入口
确认者（签字）凭什么信这个结果依据、来源、置信度、改动历史
维护者（IT/主管）出问题能不能查到运行记录、失败原因、权限日志

还有一个常被漏掉的角色：他可能是受害者——比如录入员，系统上线等于他的活被替了。这类人不配合不是技术问题，是组织问题，得提前想到。

他可能追什么
  • 「那谁付钱？」→ 通常是决策者，但他不是使用者。所以卖点对决策者讲（省多少钱、降多少风险），体验对使用者做——两套话，别混。
  • 「使用者抵触怎么办？」→ 先做「帮他干」而不是「替他干」：给候选让他确认，不给最终结论。抵触最小的时候，是系统还在帮他省事的时候。
Q1.5第③步 · 业务痛点（用代价讲，别用形容词）›
面试官原话

现在到底有多痛？

20 秒答法
「不用『效率低』这种词。用代价讲：一天多少人花多少小时、一年错几次、错一次赔多少。」
展开讲

痛必须能数。三种量化方式，至少给一种：

角度怎么算例子
人力人 × 小时 × 频次五个人每天各花两小时核单，一年约 2500 工时
风险错误率 × 单次代价每月错三单，每单返工加赔付约 X 元
机会因为慢而错过的报价慢一天，中标率掉多少

三种里「机会」最难算但最有说服力，因为它对决策者说话。「人力」最容易被接受，「风险」最容易被记住。

他可能追什么
  • 「这个数字哪来的？」→ 一线估的就说估的，别包装成系统统计。被戳穿一次，后面全不可信。
  • 「省下来的时间真的会变成钱吗？」→ 老实说：不一定。省下来的时间可能只是让人轻松点，这不丢人，但别把它算成 ROI。
Q1.6第④步 · 需求分析（要的不是「AI 全自动」）›
面试官原话

那你觉得他们真正需要什么？

20 秒答法
「不是『AI 全自动』，是四件事：把散的信息聚合起来、每条给出处、按风险分级、高风险的人来确认。」
展开讲

这四条是把「想要 AI」翻译成「能验收的需求」。全自动是愿望，这四件才是需求。

他要的翻译成什么怎么验收
「太散了，能不能一处看全」聚合原来切五个系统，现在一个页面
「它说的我不信」每条给出处点结论能跳到来源
「错的代价不一样」按风险分级高风险动作必须人工确认
「出了事谁负责」留痕与确认每次操作有记录、有签字人
他可能追什么
  • 「为什么不能全自动？」→ 因为错的代价由人承担，不由模型承担。责任在哪，确认就在哪——这句话是这一整节的根。
  • 「那全自动永远做不到吗？」→ 能做到，前提是这件事错了可逆、且能被自动检测。两个条件同时满足的，才敢放开。
Q1.7第⑤步 · AI 切入点（哪一步该 AI、哪一步不该）核心›
面试官原话

这个流程里，哪些交给 AI？

20 秒答法
「模型只干『需要理解』的活：读非结构化材料、判断语义、生成初稿。流程推进、权限校验、写库、审计，全交给代码。」
展开讲

判断标准只有一条：错了能不能重来。

  • 能重来的（生成初稿、做摘要、给候选）→ 交给模型，多试几次成本也低。
  • 不能重来的（写库、对外发送、付款、改权限）→ 交给确定性代码，而且前面必须有人。

一个反直觉的点：模型的输出不应该叫「结论」，应该叫「候选 + 置信度」。叫法一变，后面所有设计都跟着变——因为候选天然需要有人选。

这也是「模型处理语义、代码控制业务」这句话的由来：模型负责把自然语言变成结构化意图，业务规则和副作用由代码兜底。

他可能追什么
  • 「模型判断错了怎么办？」→ 模型给的是候选加置信度，不是结论。低置信的标「待确认」，不落库。
  • 「那要人来选，AI 还有什么价值？」→ 价值在「把二十个候选收成三个」。人做的是选择题，不是填空题——这两件事的耗时差好几倍。
Q1.8第⑥步 · 方案设计（输入→处理→输出→反馈）›
面试官原话

整个方案串起来是什么样？

20 秒答法
「四段闭环：输入从哪来、中间怎么处理、输出给人看什么、人改完之后怎么回流。缺第四段，系统就不会变好。」
展开讲

四段里最容易漏的是反馈。没有回流，同一个错会一直犯，而且没人知道它在犯。

段要答清楚的问题漏了会怎样
输入数据从哪来、格式如何、有没有权限做到一半发现数据拿不到
处理哪些交模型、哪些交代码、顺序是什么模型干了不该它干的活，出错无法定位
输出给人看的是结论还是候选、带不带依据人不敢用，采纳率极低
反馈人的修改回流到哪系统永远停在第一版水平
他可能追什么
  • 「反馈具体回流到哪？」→ 三类去处：改提示词（理解错了）、补数据（它不知道）、加规则（根本不该让它判断）。分不清这三类，反馈就白收。
  • 「这个闭环要多久跑一次？」→ 看错的代价。对客场景一周一次，内部报表可以一个月一次。
Q1.9第⑦步 · 技术选型（每个模块「选什么 + 为什么」成对讲）›
面试官原话

每个模块你为什么选这个？

20 秒答法
「选型要成对讲：选它，是因为要解决 X；不选另一个，是因为它会带来 Y 的代价。」
展开讲

只讲「我用了 RAG」没有含量。有含量的是这个句式：

「我没把全文塞进上下文，因为上下文放不下、成本还随长度涨；改用检索，代价是可能漏召回，所以加了阈值和『没查到就说没查到』。」

每一句都包含三样：选了什么、为什么、代价是什么。缺了代价，听起来就像在背广告。

模块常见选法代价（必须说出来）
流程控制Workflow / 状态机不够灵活，新分支要改代码
知识注入RAG可能漏召回；要维护切片和索引
能力调用Tool + Schema工具多了模型会选错，要白名单和描述质量
判断类任务Agent不可预测，要评测、要预算门禁
输出约束JSON Schema + 解析闸门模型有时会破坏格式，要重试和兜底
他可能追什么
  • 「如果不用 RAG 呢？」→ 给备选和它的代价，说明你比较过。答「那就没法做」是最差的回答。
  • 「这个选型是你定的还是团队定的？」→ 老实分：哪些我拍板、哪些是既定方案我只是接入。
Q1.10第⑧步 · 编排方式（Agent / Skill / Tool / Workflow / 规则怎么分）›
面试官原话

这几个能力怎么编排？

20 秒答法
「按『谁决定下一步』分：路径固定走 Workflow，单步动作封 Tool，需要模型自己判断的才给 Agent，常用组合沉成 Skill，确定性约束写成规则。」
展开讲

一个真实系统里通常四种都有。全是 Agent 是最贵的做法，也是最难调的。

类型谁决定在系统里的位置
Workflow人写死主骨架：取数 → 校验 → 综合 → 发布
Tool模型决定调不调取数、查询、写草稿这些原子动作
Agent模型自己判断只在「下一步不确定」的那一段
Skill人被调用一套固定做法：查什么、怎么判、什么时候停
规则不涉及判断预算上限、权限白名单、必填校验

比例参考：骨架是 Workflow，中间一层 Tool，Agent 只占一小段，规则散在边界上。谁把 Agent 当骨架，谁就在给自己做运维负担。

他可能追什么
  • 「怎么防止 Agent 乱调工具？」→ 三样都要：白名单（只给该给的）、参数 Schema（类型和取值卡住）、预算门禁（调太多次直接停）。
  • 「多个 Agent 怎么协作？」→ 按角色拆，各自有权限和上下文；子运行之间不共享历史，要共享就显式传。
Q1.11第⑨步 · 数据来源（在哪、缺什么、能不能补）›
面试官原话

数据从哪来？

20 秒答法
「三件事要说清：数据在哪、缺哪块、缺的那块短期能不能补。缺的说缺，别假设它有。」
展开讲

数据是 POC 的第一道坎，不是模型。多数项目死在「数据拿不到」，不是「模型不行」。

「缺什么」要能具体到维度，不能只说「数据不太全」。比如：有财务数据、没有评级数据；有国内行情、没有海外行情。说得出缺哪块，才说得出方案怎么降级。

第三件事最关键：短期能不能补。能补就排进计划，不能补就设计降级——但降级必须在结果里看得见，不能悄悄少一块。

他可能追什么
  • 「有一块拿不到怎么办？」→ 降级成「不可用」并且让它出现在结果里，绝不静默删掉这个维度。少一个维度要让人看见。
  • 「数据质量差怎么办？」→ 按来源定级（官方接口 / 第三方 / 网页抓取），低可信的降权并标注，不让它当权威。
Q1.12第⑩步 · 数据处理（统一格式、低可信降权、不假装覆盖）›
面试官原话

拿到数据之后怎么处理？

20 秒答法
「统一成一套字段；来源可信度低的降权并标注；没有的数据就写没有，不能假装覆盖。」
展开讲

最后一句是红线。把「没查到」写成「未提及」，下游会当成「确认没有」——这是最隐蔽的一类错，因为格式全对、看起来一切正常。

做法为什么不做的后果
统一字段不同来源字段名和粒度都不同下游拼接时张冠李戴
可信度降权网页抓的和官方接口不是一个可信级别野数据盖过权威数据
缺失要显式「没有」和「没查」是两件事结论假装完整
他可能追什么
  • 「怎么判断可信度？」→ 按来源定级，不同级不同权重。级别由人定一次，之后自动套。
  • 「缺失显式化会不会让人不敢用？」→ 会，但这是对的。不敢用说明他看懂了，比糊里糊涂用强。
Q1.13第⑪步 · POC → 上线（先定义什么算成功）›
面试官原话

怎么从验证走到上线？

20 秒答法
「先定成功标准，再动手。POC 只承诺三件能验证的事：数据进不进得来、效果压不压得住、用户认不认可。三件都过才谈生产。」
展开讲

POC 不是「做个 demo 看看」，是有明确通过线的实验。没有通过线的 POC，做完了只能靠感觉判断，然后就一直拖着。

验证项怎么算过没过怎么办
数据进得来目标字段能自动取到 X%先解决数据，别做模型
效果压得住比人工基线的错误率低，或修正率可接受缩小场景，或降级成人辅助
用户认可试用的人愿意继续用改交互，不改模型——多数是「不敢信」不是「不准」

顺序要注意：三件里只要有任意一件不过，就不要往生产推。推上去也会被弃用。

他可能追什么
  • 「通过线定多少？」→ 由业务定，不由我定。我给的是「现在人工的错误率是多少」，以此为基线谈。
  • 「POC 做多久？」→ 做到能回答那三个问题就停，不是做完整功能。做完整功能那叫原型。
Q1.14第⑫步 · 指标 + 人工 + 反馈闭环›
面试官原话

上线之后怎么证明它有用？

20 秒答法
「三类指标：效果（准确率、修正率）、使用（采纳率、日活）、风险（越权率、误发数）。再加人工兜底点和 Bad Case 回流。」
展开讲

只看准确率会骗人——没人用的系统，准确率 99% 也没价值。

类指标它其实在回答什么
效果准确率、修正率、召回率它做得对不对
使用采纳率、日活、单次耗时人愿不愿意用
风险越权率、误发数、人工拦截数它有没有捅娄子

采纳率低往往是「不敢信」而不是「不准」，这两种情况的改法完全不同：前者改交互（给依据、给对比），后者改模型。

人工兜底点要写死在流程里，不能靠人自觉——靠自觉的兜底，忙起来第一个被跳过。

他可能追什么
  • 「Bad Case 怎么回流？」→ 每条进数据集；能机械断言的写成用例，断言不了的进人工评审。两边都不进的，就是盲区，要承认有盲区。
  • 「指标掉了怎么查？」→ 先分是模型变了、数据变了、还是用户变了。三者混在一起看，永远查不出来。
Q1.15完整示范：企业材料智能录入（12 步走一遍）›
面试官原话

那你把这 12 步在一个具体场景上走一遍。

20 秒答法
「一句话串起来：材料录入不是让模型直接写库，而是模型处理语义、代码控制业务。模型只把材料变成结构化草稿，阶段推进、权限校验、落库都由代码兜底，每次写操作前都有一次人工确认。」
展开讲

这是结构示范，不是真实经历。照抄走位，把「合同/单据」换成你实际做过的业务即可。

步内容
① 业务背景企业合同/单据录入：字段多、要跨系统查对方主体与档案、附件要解析、容易漏填错填。
② 用户与角色录入员（执行，逐字段填）、法务或主管（确认，签章审批）、IT（看权限和日志）。
③ 痛点跨系统找数据慢；填错要返工；附件内容没人看全；责任难追。
④ 需求要的是「把非结构化材料变成可确认、可校验、可落库的结构化草稿」，不是「AI 自动把合同签了」。
⑤ AI 切入点模型做语义理解、字段抽取、对手方匹配；流程推进、校验、权限、落库全归代码。
⑥ 方案上传或描述 → 解析抽取 → 字段推荐与候选匹配 → 分阶段让用户确认 → 校验 → 落库 → 全程留痕。
⑦ 技术选型阶段用 Workflow/状态机保证顺序；模型只在需要语义处接管；附件解析用 OCR；查询封成受控工具。
⑧ 编排按业务类型路由；不同录入对象隔离成子流程；草稿和阶段状态持久化，中断能续。
⑨ 数据业务库（合同/客户/供应商）+ 附件 + 企业公开信息；权限在服务层过滤。
⑩ 处理字段统一成一套 Schema；低可信候选标「待确认」，不让模型直接落库。
⑪ POC先拿 50 份真实单据：解析成功率 → 抽取准确率 → 候选命中率 → 人工修正率，达到阈值再扩。
⑫ 指标字段准确率、修正率、草稿确认率、录入耗时对比、越权率≈0；高风险写操作必须人工确认；Bad Case 回流调提示词、Schema、规则。
他可能追什么
  • 「这个案例是你做过的吗？」→ 老实说这是标准场景，我实际做过的是另一个业务，但走位一样。然后把话拐到你真实的项目上。
Q1.16二面 / 解决方案岗要额外证明的 3 件事›
面试官原话

（二面或售前岗）你凭什么能面对客户？

20 秒答法
「三件：开场先问业务，不先讲技术；每个技术回答挂一个 ROI；最后一定主动讲风险和备选。」
展开讲
  1. 开场先问业务（见 Q1.0）——这是区分「解决方案型」和「开发者」的关键信号。技术面可以上来讲架构，售前面不行。
  2. 每个技术回答挂一个 ROI——讲完技术补一句「落地时我会先验证 X 再推 Y，价值是省了多少人、或者降了多少风险」。
  3. 主动讲风险与备选——结尾一定带「最大的风险是……，备选是……」。客户最看重的不是你方案多好，是你知道边界在哪、出问题怎么办。

这三件事的共同点：都在证明你替对方想过，而不是在证明你技术强。

他可能追什么
  • 「你凭什么觉得客户会信你？」→ 不靠说服，靠把不确定的地方先说出来。先说「这三处我不确定」，后面说的才有人信。
Q1.17白板 5 步（要你画图时）›
面试官原话

来，白板上画一下。

20 秒答法
「五步画：先问两个澄清问题；再定骨架；然后圈出最小 POC；接着画安全阀；最后用 ROI 收尾。」
展开讲

画图顺序固定，别边想边画：

  1. 先问 2 个澄清问题（最痛的风险？有没有数据和台账？）——问的时候笔别动，问完再画。
  2. 定骨架，从左到右一条线：业务对象 → 数据 → 统一模型/事件 → AI 能力 → Agent/Skill → 人工与权限 → 闭环与沉淀。
  3. 圈出最小 POC：数据可及 + 流程确定 + 价值直接 + 能评测，四条同时满足的那一段，用圈标出来。
  4. 画安全阀：AI 初筛 → 人复核 → 全留痕 → 高风险人工；召回失败不静默。
  5. ROI 收尾：不是「省人力」，是「降风险、提速度、保合规」——挑最贴他业务的那一个说。

画的时候留白，因为面试官一定会指着某一块问「这里为什么这么放」。留白的地方就是你准备展开的地方。

他可能追什么
  • 「这块为什么放这儿？」→ 按数据流答：它的输入从哪来、输出给谁用。不要按「技术分层」答。
Q1.18收尾金句（三选一）›
面试官原话

（讲完方案，最后一句说什么）

20 秒答法
「我设计的每一步都有数据来源和人工节点——这是证据链管理，不是模型表演。」
展开讲

三句，按场合挑：

金句什么时候用
「我设计的每一步都有数据来源和人工节点——这是证据链管理，不是模型表演。」对方明显在担心「AI 靠不靠谱」时

  • 无追问。但这一句往往是他记住你的那句。

项目全链路表达

面试官要你「讲一遍做过的东西」时，不是报项目，是给出一条能证明你适合这个岗的能力主线。 · 12 张

Q2.1一页总览：30–60 秒先给他一张地图必背›
面试官原话

先整体讲讲你做过什么。

20 秒答法
「我做的是把业务流程拆成 Agent 能干活、人能管、效果能回查的系统。两段：投研那边把取数、综合、出报告做成一条能回查的流水线；客户经营那边把系统的主要动作封成六十多个工具，所有对客动作只出草稿、必须人确认。前一个错了是答案不准，后一个错了是给客户发错消息，后者难得多。」
展开讲

开场 30–60 秒就这一小段，目的是把面试官钉在你最想被追问的两块上，而不是把两段经历平均讲完。

结构固定四句：

  1. 我做的是一类什么事（一句话，不带技术名词）
  2. 两段经历各一句（只给「从什么变成什么」）
  3. 一个具体判断（两段的难度差在哪）
  4. 为什么来这个岗

第三句是这段的分水岭。没有判断，就是复述简历；有判断，他会顺着你的判断往下问——而那是你准备好的地方。

他可能追什么
  • 「你说的两段，时间上是什么关系？」→ 按实际说：前后两段实习，不是同时。别让人误以为是一个大项目。
  • 「有共享的代码或数据吗？」→ 没有。共享的是方法：状态怎么管、技能怎么 SOP 化、评测怎么回流。
Q2.2经历关系表（防止把两段吹成一家公司的大系统）›
面试官原话

这两段经历是什么关系？

20 秒答法
「它们是两段独立的实习，没有共享数据库和代码。能串起来的是方法：状态怎么管、技能怎么 SOP 化、评测怎么回流。」
展开讲
投研 Agent客户经营 Agent
上游输入行情、财报、新闻等外部数据源客户系统的联系人、商机、会话、知识库
下游输出带依据的研究报告带三分标注的客户摘要、对客消息草稿
核心状态研究计划的进度、每项的成败、检查点会话状态、待确认动作、权限范围
失败兜底单项失败降级成「不可用」，整轮标「部分成功」无直接发送能力，只能出草稿等人确认
我的职责上下文装配独立实现；12 个确定性评测器里接入并写了 2 个参与落地：工具契约与部分编排

红线：没有共享关系的项目，只能从「能力演进 / 方法复用」角度串，绝不虚构共享数据库、共享代码、共享模型。吹成一个大系统，一问架构就崩。

他可能追什么
  • 「那你说说方法是怎么复用的？」→ 举一条具体的：投研那边「失败要显式」，搬到客户经营就是「查不到就说查不到，不能写成未提及」。同一个原则，两个落点。
Q2.3单个项目怎么讲：90 秒版 / 3 分钟版›
面试官原话

挑一个项目，详细讲讲。

20 秒答法
「90 秒版说四件：业务瓶颈、链路、我负责的模块、失败怎么处理。要展开再补三件：为什么这么拆、哪些交给规则和人工、哪里需要引用和状态机。」
展开讲

90 秒版的顺序不能换：

  1. 业务瓶颈（一句话，多痛）
  2. 链路（输入 → 处理 → 输出，一段一句）
  3. 我负责的模块（明确说边界）
  4. 失败怎么处理（这条最容易被忽略，也最能证明你真做过）

3 分钟版再补三件：

  • 为什么这么拆（而不是一个大 Agent）
  • 哪些交给规则系统、哪些交给人（边界在哪）
  • 哪里必须用引用、Schema、状态机（为什么不能靠模型自觉）

提示：90 秒讲完就停，等他问。一口气讲三分钟，他会失去追问的欲望——而追问才是你展示深度的机会。

他可能追什么
  • 「你负责的模块，具体到什么程度？」→ 用「能讲每一行 / 参与落地 / 只读通」三档说，别含糊。
  • 「失败处理具体是什么？」→ 举一个真实机制：某项取数失败不静默删维度，而是标「不可用」进结果，整轮降级成「部分成功」。
Q2.4两段经历凭什么能串起来›
面试官原话

这两段经历，为什么能放在一起讲？

20 秒答法
「串它们的不是行业，是三件方法：状态怎么管、技能怎么 SOP 化、评测怎么回流。行业换一个，这三件还是要用。」
展开讲

面试官问这句，是在查一件事：你是真的有一以贯之的方法，还是把三个不相关的小项目拼在一起凑简历。

三件方法各自要能举一个跨项目的例子：

方法投研那边客户经营那边
状态管理研究计划进度、检查点、可续跑会话状态、待确认动作、阶段持久化
技能 SOP 化技能只给目录不给正文，按需加载工具按已购包筛选，描述即契约
Trace–Eval–Bad Case86 条用例、8 条真实回归运行记录脱敏、失败原因可查

这样答的好处：他不会再问「为什么行业差这么远还能通用」，因为你已经先回答了——通用的是这三件，不是行业知识。

他可能追什么
  • 「行业差这么远，你凭什么说经验通用？」→ 因为变的只是口径，不变的是「事实从哪来、错了谁兜、改完怎么验」这三问。任何行业都要答这三问。
  • 「那行业知识重要吗？」→ 重要，而且我没有。我给的是搭法，行业口径得靠人教——这个边界要主动说。
Q2.5跨项目能力映射（JD 每个词 ← 哪段证据）›
面试官原话

你为什么适合这个岗位？

20 秒答法
「我不空说适合。您 JD 上的每个能力词，我能指出对应哪段经历、哪件具体事；指不出来的，我直接说没有。」
展开讲

做法：把 JD 拆成能力词，一个个对。对不上的不要硬凑——空一格比编一格安全。

岗位能力我的证据强度
Agent 编排投研的十段装配 + 四步取数；客户经营的四 Agent 与工具路由强
工具 / 契约设计60+ 工具的参数与描述；白名单与按已购包筛选强
评测与回归86 条用例、12 个确定性评测器、8 条真实回归强

最后一行是加分项不是减分项：主动标出弱项，前三行的强项才有人信。

他可能追什么
  • 「你说落地，上过线吗？多少人在用？」→ 老实给范围：内部可用、有小范围用户。别编 DAU。
Q2.6为什么不用纯大模型直答›
面试官原话

直接让模型回答不就行了，为什么要搞这么多层？

20 秒答法
「因为它答得流畅不代表答得对。纯直答缺四样：事实来源、权限边界、执行状态、出错可查。所以模型负责理解和生成，事实、规则、执行、审计交给外部系统。」
展开讲
缺什么纯直答的后果补法
事实来源编数字，而且编得很像工具读事实 + 引用校验
权限边界答出他不该看的数据服务层过滤，模型只看得到该看的
执行状态说「已经办好了」，其实没办状态机 + 工具真实调用 + 结果回执
出错可查错了不知道错在哪一步运行记录 + 分步留痕

一句话记：模型负责理解和生成，事实、规则、执行、审计交给外部系统。

他可能追什么
  • 「那这样模型还有什么用？」→ 它把非结构化的东西变成结构化的候选。这一步以前只能靠人。
Q2.7为什么 Agent 不能直接做执行（RPA / API 的角色）›
面试官原话

让 Agent 自己去点、自己去发不就行了？

20 秒答法
「职责不同。Agent 生成参数，RPA 或 API 做确定性动作——只有这样才敢重试、才能人工接管、出了问题才知道是哪一步。」
展开讲

三个理由，缺一个都不该让 Agent 直接执行：

  1. 不可重试：Agent 每跑一次结果可能不一样，失败了没法简单重放。
  2. 不可接管：动作藏在模型的黑箱里，人想接手时不知道它做到哪了。
  3. 不可定位：出错时说不清是理解错了、参数错了，还是执行本身错了。

正确分工：模型决定「做什么、参数是什么」，执行器负责「真的做」。执行器是确定的，所以能重试、能回滚、能审计。

这也是客户经营那个项目「对客动作不给直接发送能力」的原因：发送是执行，执行必须落在确定性代码上，并且前面有人点确认。

他可能追什么
  • 「那 Agent 只出参数，价值不大吧？」→ 价值在把「人填参数」变成「人选参数」。前者要查五个系统，后者只要点一下。
Q2.8为什么要有 RAG 和状态机›
面试官原话

RAG 和状态机，各解决什么问题？

20 秒答法
「RAG 让输入有依据，状态机让执行有状态、能续跑、能追责。一个管『它凭什么这么说』，一个管『它做到哪一步了』。」
展开讲
RAG状态机
解决模型不知道，或记错了多步流程中断、重复、说不清进度
不做会怎样编造，或者拿过期知识答重跑时重复扣费、重复发消息；出错找不到断点
代价可能漏召回；要维护切片与索引流程不灵活，加分支要改代码

两者配合的典型场景：先按状态机推进阶段，每个阶段用到知识时才检索——而不是一次性把所有知识塞进上下文。

他可能追什么
  • 「RAG 漏召回怎么办？」→ 阈值 + 「没查到就说没查到」，绝不拿相似内容顶上。这是可靠性问题不是体验问题。
  • 「状态机不能覆盖所有情况怎么办？」→ 留一个「异常待人工」的终态，不要硬编码所有分支。
Q2.9怎么避免幻觉、误发、无依据›
面试官原话

AI 胡说八道怎么办？发错东西怎么办？

20 秒答法
「六道闸，从便宜到贵：工具读事实、Schema 卡结构、引用校验、置信度分级、人工确认、Bad Case 回归。前四道自动，第五道靠流程，第六道靠习惯。」
展开讲
闸挡住什么挡不住什么
工具读事实凭记忆编数字工具返回本身是错的
Schema 约束格式乱、字段缺字段填了但填错（比如时间粒度选错）
引用校验说了但没依据依据挂错地方
置信度分级低可信内容被当结论模型自信地错
人工确认不可逆动作出错人自己也看走眼
Bad Case 回归同一个错犯第二次全新的错

要能主动说出挡不住的：六道闸全过一遍，仍然会有「格式全对、参数合法、但业务语义错」的情况——那一类只能靠评测用例和人工评审兜。

他可能追什么
  • 「六道都过还会错吗？」→ 会。举个真实的：模型把盘中数据当多月 K 线用，格式全对、工具也调了，只是时间粒度选错。这类错只能靠事后回归抓。
Q2.10不能确定的部分怎么答›
面试官原话

这个细节你说得清吗？/ 这块是你做的吗？

20 秒答法
「这部分我当时没直接负责，我能确认的是……；要往下说，得回到我实际参与的那一块。」
展开讲

这个句式有三个作用：不编、不显得心虚、把话头拉回你的主场。

三类要主动标出来的：

  • 没动手的：「安全那一层我只读到调用链，四层各挡什么我能讲，里面的规则我没改过。」
  • 团队定的：「评测框架是团队先定的，我负责把 12 个评测器接进去。」
  • 不确定的：「这个数字我记得是量级，具体值我要回去查记录。」

反过来，最危险的是硬答：一旦被追问两层答不上来，前面答对的所有内容都会被打折。

他可能追什么
  • 「你这么说是不是没做过？」→ 不是。把能做的那部分讲细，用细节证明你确实在里面。
Q2.11三个压力追问（提前备好）›
面试官原话

（面试官挑刺时最常问的三句）

20 秒答法
「三句我都想过了：为什么能串、方法怎么迁移、场景差这么远凭什么说通用。回答都落在同一处——方法迁移三件套。」
展开讲
他问你怎么答
「你两段经历为什么能串起来，而不是几个不相关的小项目？」串的是方法不是行业：状态管理、技能 SOP 化、Trace-Eval-Bad Case 回流。各举一个跨项目的例子。
「某段的方法怎么迁移到另一段？」举一条具体的：「失败要显式」在投研是标不可用，在客户经营是查不到就说查不到。
「行业差异这么大，你凭什么说经验通用？」变的只是口径，不变的是三问：事实从哪来、错了谁兜、改完怎么验。行业知识我没有，得靠人教。

三句的共同答案叫方法迁移三件套：状态管理 / 技能 SOP 化 / Trace–Eval–Bad Case 回流。记住这三个词，三句都能接。

他可能追什么
  • 「你说的三件套，有反例吗？什么情况下不成立？」→ 有。如果两边连「什么算错」都不一样，方法迁移就失效——那时候得先对齐验收标准。

20 秒答法
「讲之前我会过五条：每句『我负责』都能回到简历、整体架构标了参考来源、没把握的标待确认、先讲业务再讲技术、没把不相关项目硬串成一个系统。」
展开讲
  1. 每句「我负责」都能回到简历或项目材料——对不上的删掉。
  2. 公司整体架构、开源参考都标了【架构参考 / 开源参考】——别把别人搭的说成自己搭的。
  3. 没把握的细节都标了【待确认】——被问到时老实标记，比现编强。
  4. 每个项目都先讲业务目标和数据流，再讲 Agent / RAG / MCP / Eval。
  5. 没有把不相关的项目硬串成「一个系统」。

这五条里最容易犯的是第 5 条。串得太顺、听起来太完整，反而会让面试官怀疑——真实项目都是东一块西一块的。
