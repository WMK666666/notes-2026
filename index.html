Q0.130 秒定位：你是做什么的必背›
面试官原话

先简单介绍一下自己，用一两句话说清你是做什么的。

20 秒答法
「我把业务流程拆成 Agent 能干活、人能管、效果能回查的系统。具体做过两段：一段让研究员从翻十几个数据源，变成看一份每条结论都有出处的报告；一段让销售不用切五个系统，就能查清一个客户的来龙去脉。」
背诵版 · 照着念

我叫【】，【】大学软件工程专业，【】届。这两年就干一件事：把 AI 接进真实业务里，让它真能替人干活，出错还查得到是哪一步坏的。

具体两段。第一段在【某私募】做投研助手，研究员原来开十几个网页翻公告和研报，一份材料大半天；现在写一句话，出来一份报告，每条结论都能点回原文。第二段在【某跨境公司】做客户经营，销售查客户原来要跳五个系统；现在一句话，历史沟通、订单、风险点一起给出来。

概括成三个词：能干活、人能管、效果能回查。

面试官原话

你为什么来我们公司？你了解我们是做什么的吗？

20 秒答法
「【待你填】三句：① 这家公司靠什么赚钱、钱从谁口袋里出；② 这个行业最痛的是哪一段、AI 正在改哪一段；③ 这个岗位最想证明的一个能力，我用哪段经历接。」

来之前我查了三件事。

第一，这家公司靠什么赚钱、钱从谁口袋里出。【一句，写清谁付钱、为什么付】

Q0.3技术选型口诀：五个词怎么分必背›
面试官原话

这个场景你打算用 Workflow 还是 Agent？为什么？

20 秒答法
「固定流程走 Workflow，固定动作用 Tool，复杂任务才上 Agent，稳定能力沉成 Skill，外部知识走 RAG。够用最简，不够才加复杂度——不是越智能越好，是越可控越好。」
背诵版 · 照着念

这五个词我不按难不难分，按谁决定下一步分。

流程能定下来，就走 Workflow，别交给模型。固定动作，比如查一次客户、拉一份财报，封成 Tool，模型决定调不调。路径真的不确定、要看上一步结果才知道下一步，才上 Agent。一组常用动作加约束沉成 Skill，反复用。模型是不知道而不是不会做，才补 RAG。

一句话记：流程能定，就别交给模型定。每交给模型一步，就多一处不可预测，也多一处要评测的地方。

展开讲

五个词的分界不在「难不难」，在谁决定下一步：

词谁决定下一步什么时候用它
Workflow人，写死的步骤和分支都能提前定下来
Tool模型决定调不调，但动作本身是确定的取数、查询、写入这类固定动作
Agent模型自己判断路径不预先确定，要边看边决定
Skill人，作为一段可复用能力被调用一组常用动作 + 提示词 + 约束，反复要用
RAG不涉及决定，只负责喂料模型「不知道」而不是「不会做」

一句话记：流程能定就别交给模型定。每交给模型一步，就多一处不可预测，也多一处要评测的地方。

他可能追什么
  • 「你们项目里哪里用了 Agent，哪里其实不需要？」→ 取数是 Workflow（四项并发、顺序固定、单项 20 秒超时）；只有综合判断那一步才交给模型。
  • 「为什么不用一个大 Agent 全做完？」→ 角色、上下文、工具权限、责任边界分不清；出错时定位不到是哪一段坏的。
  • 「Skill 和 Tool 差在哪？」→ Tool 是原子动作（查一次客户），Skill 是一套做法（怎么查、查完怎么判、什么情况停手）。

Q0.6场景题走位 5 步（紧张时用这个）必背›
面试官原话

给你一个场景，你怎么设计？

20 秒答法
「五步：先问两个澄清问题；再定骨架——业务对象、数据、AI 能力、编排、人工与权限、闭环；然后挑最小可评测的场景做 POC；接着画安全阀；最后用 ROI 收尾。」
背诵版 · 照着念

时间紧，或者对方只是随口一问，我走五步，不铺开讲十二步。

第一，先问两个澄清问题：最怕的风险是什么、数据和台账有没有。

第二，定骨架，从左到右一条线：业务对象、数据、AI 能力、编排、人工与权限、闭环。

第三，圈出最小 POC：数据可及、流程确定、价值直接、能评测，四条同时满足的那一段。

第四，画安全阀：AI 初筛、人复核、全留痕、高风险必须人工。

第五，用 ROI 收尾。不讲省人力，讲降风险、提速度、保合规。

顺序不能换。先问再定，先小再大，先安全阀再谈价值。

展开讲

这五步是 12 步的压缩版。时间紧、或者对方只是随口一问，用这五步就够；他要是往下追，再展开成 12 步（板块 1）。

顺序不能换，三条理由：

  • 先问再定：不问就出方案，等于假设了一堆没验证的前提。
  • 先小再大：一上来讲全量架构，他没法判断你说得对不对，只能判断你会不会画图。
  • 先安全阀再谈价值：业务方最怕的是「AI 捅娄子」，不是「AI 不够聪明」。先给兜底，他才听得进价值。
他可能追什么
  • 「最小的 POC 怎么挑？」→ 数据可及、流程确定、价值直接、结果能评测，四条同时满足的那个。缺一条就换个场景。
  • 「ROI 怎么算？」→ 拿现在的人工基线算：几个人、一天几小时、一年错几次。算不出来就说明还没到能做的时候。

它假设的场景。 大厂校招技术面，一面 45 分钟、二面 60 分钟。面试官手里有你那份简历，会顺着简历上的每一个名词往下挖三层。他不考你背没背过 RAG 的定义，他考的是：这个设计当时还有什么别的走法、为什么没走、代价落在谁身上。

每道题的四个部分。

——把机制讲成白话：这东西在项目里到底干什么、容易在哪出错、该记住哪一句。

全篇统一一个答题公式：先说判断 → 再给机制 → 再说取舍 → 最后给边界。

先给判断（一句话回答他问的那件事，是、不是、能、不能），再给机制（函数名、常量、具体数字），再说取舍（当时还考虑过什么、为什么没选、代价谁承担），最后说边界（这套东西在什么情况下不管用）。四句话一层层往下，正好对上他的三层追问。

三条纪律。

第一，说得出函数名和数字，说不出就承认没读过那一块。校招面试官对「不知道」的容忍度，远高于对「编一个」的容忍度。承认一句「这块我只读到调用层，没进到实现」，比含糊过去强十倍。

第二，每个「我们」后面都要能接上「我具体做了哪一段」。这是最容易翻车的地方：讲技术讲得很顺，面试官插一句「这块是你写的吗」，答不上来，前面讲的深度全部打折。

第三，主动说缺口。这两套系统都有真实的、可指认的缺口。面试官问「有什么没做好」，你答「都挺好的」，他立刻知道你没进过生产；你答得出具体哪一处漏了、为什么漏、怎么兜，他反而信你。

一个提醒。 口播里的代码细节，是「你应该能讲到的深度」，不是「你必须说成自己写的」。讲到哪一层、怎么表述贡献归属，由后面「贡献矩阵」那张表决定。

判据：每一层都要能举一个只有作者才知道的细节。这种细节不在设计文档里，是踩过坑才长出来的。

他要追的话
  • 「那你凭什么证明是你写的？」举两个：①检查点块为什么写在最前面、又要在开头补一句「以历史为准」——因为模型把越靠前的内容读成越权威的指令，而检查点是上一回合的快照，比客户刚说的话旧；②工作台那条路径的发送候选是写死空数组的，所以我简历上不写「工作台能产出对客消息草稿」，只写对客动作独立确认。
红线
  • 不要说「都是我一个人做的」。校招项目体量摆在那儿，这句话一说出来，面试官立刻会去挑最薄的那块问。
  • 不要说「团队做的我不清楚」。这等于承认你只是在旁边看。
  • 不要用「我主要负责……」开头然后不说具体。「负责」两个字在这张桌上没有分量，有分量的是「我改了哪一行、为什么改」。
Q1.3你说你是做 AI 应用的，那和 AI 算法岗有什么区别？›
他在测什么

岗位认知。答不清这条界线的人，通常会在入职后发现「这活儿跟我想的不一样」。

照着说
「一句话切开：算法岗改的是模型本身——数据、训练、微调、评测体系；我改的是模型外面那一圈——它看到什么上下文、能调什么工具、调完的结果怎么核、出错怎么兜。」
「用我自己的项目举证：模型能力是给定的，我没动过它一个参数。我能动的是三件事——上下文里放什么（十段有序装配、技能只给目录不给正文）、工具列表里挂什么（二十项能力注册表、六十三个 MCP 工具按已购包筛选）、结果怎么判对错（十二个确定性评测器加语义评审）。这两个项目从头到尾就在做这三件事。」
「所以我不做模型选型的理论推导，我做的是『给定这个模型，怎么让它在业务里不出错』。」
这是什么

界线一句话：改模型 vs 改模型外面那圈。

说清它的实际好处：面试官知道该往哪问。 你说「我做应用层」，他就不会拿 loss 函数来考你；你要说「我懂算法」，他下一句就是「你微调用的什么损失函数」。

他要追的话
  • 「那你算 AI 工程师吗？」算，做的是应用层的工程约束。这个岗位在不同公司叫法不一样——AI 应用开发、大模型应用开发、Agent 应用开发，说的是同一件事：把现成的模型能力接进业务系统，并且让它可治理、可观测、可回归。
红线
  • 不要为了显得厉害，把算法侧的东西说成自己做过。面试官问一句「你微调用的什么 loss」就穿了。
  • 反过来也不要过度自谦说「我就是调调 prompt」。这句话会把你两个项目的工程量全部抹掉。
Q1.4两段实习之间隔了一个月，为什么换？›
他在测什么

稳定性和主动性。校招面试官对「短期两段」格外敏感，怕的是「待不住」。

照着说
「两段不是换方向，是同一条线的两段。」
「前一段偏研究型任务：长链路、要出报告、要能回查依据。后一段偏业务治理：同样的 Agent，但要管权限、管副作用、管对客动作。做完前一段我才知道，真正难的不是让它出结果，是让它出错的时候不伤到人。」
「所以换的原因是补上『治理』这一块。研究型 Agent 的失败代价是答案不准，业务型 Agent 的失败代价是给客户发错消息——后者才是工程上真正难的部分。这两段加起来，才是一个完整的应用层画像。」
这是什么

他问的是「为什么走」，其实在听「为什么连得上」。所以答案不是解释离职，是证明这两段能接成一条线。

结构：先给延续性，再给换的原因，最后收一句结论。

红线
  • 不要说前一家公司的坏话，一个字都不要。
  • 不要说「想换个环境」「想多学点东西」。这两句在他耳朵里等于「没想清楚」。
Q1.5明天让你负责一个没接触过的模块，第一步是什么？›
他在测什么

不是考你会不会这个模块，是考你会不会「先看清楚再动手」。没经验的人容易犯两个错：一上手就改代码，或者先读三天文档不敢跑。

照着说
「第一步不动代码，也不急着把文件读完。我先找三样东西：这个模块从哪进来、数据从哪来到哪去、哪条路径能从头跑通一遍。」
「做法是先跑起来，再倒着读。找一条最短的链路打日志跑一遍，把入口、出口、中间经过的函数摸清楚，然后只读这条链路上的代码，不相关的先放着。这样一天之内能拿到一个能用的认识，而不是读了一堆不知道用在哪的文件。」
「这三样清楚了才敢动手。我提开源项目的 PR 都是这个路子：先顺着调用链读，读到能说清「改这里会影响谁」，再动第一行。」
这是什么

陌生模块的难点不是「看不懂」，是「不知道哪段重要」。先跑通一条路径，等于先给自己画出一条主干，剩下的代码都是挂在这条主干上的枝叶。没有主干，读得越多越乱。

他要追的话
  • 「文档不读吗？」读，但只用来确认「这个模块该干什么」，不用来学实现。文档常常落后于代码，尤其是改过好几轮的地方。
  • 「一天读不完怎么办？」那就先交付「我读通了哪一条路径」，别交付「我读了一半」。半懂比不懂危险，它会让人直接动手改。
  • 「怎么证明你读懂了？」能画出调用链，还能指出「改这一行会影响谁」。说不清影响面的，就是没读懂。
红线
  • 不要说「先看文档、再看代码、最后动手」。这是三个动作的名字，没回答「看什么」。
Q1.6现在有一个想法，如何快速验证能否实现？›
他在测什么

会不会把「验证」做成「开发」。很多人一上来就排三周，三周后才发现路走不通。

照着说
「先找出这个想法里最贵的那条假设——它一旦不成立，整个方案就白做的那条。然后只验这一条，别的一概不碰。」
「手段尽量选最便宜的：能不能先用一个一次性脚本跑通？能不能先写一条注定会失败的测试，看它到底红在哪。我在项目里验「综合阶段能不能真的禁掉工具」，做法很小——先让它调一次，看拦不拦得住，拦得住才谈后面怎么设计。」
「判据是半天到一天之内拿到「行」或「不行」。拿不到，说明我把验证做成了开发，得往下砍。」
这是什么

快速验证的本质是先证伪最贵的那条，不是先做最容易的部分。容易的部分做完了，你会以为自己进展顺利，其实最该问的那条还没问。

他要追的话
  • 「怎么找最贵的假设？」问一句：这个方案里，哪一步我没做过、也没有现成例子可抄？那一步通常就是。
  • 「验证做到什么程度算够？」能回答「行或不行」就够，不需要跑通全流程。跑通全流程那叫原型，不叫验证。
  • 「验证失败了呢？」失败要记下两件事：卡在哪、边界在哪。这比成功有用——下次能直接排除一整类方案。
红线
  • 不要说「先做个 demo 看看」。「看看」没有判据，做完了也不知道算不算行。
Q1.7平时了解新技术的渠道是什么？›
他在测什么

是不是真的在学，还是在背简历。答「看公众号」「刷短视频」会被直接归类。

照着说
「主渠道是官方文档和发布说明，不是二手解读。比如 Next.js 16 把 middleware 改名成 proxy.ts，我是从发布说明看到的——转述的文章只说「改名了」，不说它同时把运行时固定到了 Node，而后半句才影响设计。」
「第二是源码和 issue。我给八个开源项目提过 PR，每次都是先读代码，再翻 issue 里别人踩过的坑。issue 比文档值钱的地方在于：它记的是设计者当初没想到什么。」
「第三是 review。提上去被打回来，维护者一句「这里不该这么改」，比我读三天都管用。」
这是什么

渠道之间的差别不在「新不新」，在一手还是二手。文档、issue、review 都是一手；解读和总结是二手，二手一定会丢掉条件——而条件恰恰是你要判断的东西。

他要追的话
  • 「看论文吗？」工程向的会看，纯算法的不看。我做应用层，模型的训练细节用不上，但评测方法和上下文管理的思路能用。
  • 「英文文档看着吃力吗？」技术文档不吃力，读得慢但读得完。真正费劲的是长 issue 里的来回讨论。
  • 「怎么判断一个新技术值不值得学？」看它解决的是不是我遇到过的问题。没遇到过的，先记着不动手。
红线
  • 不要说「我关注了很多技术博主」。这句话证明你关注人，不证明你关注技术。

二、Folio：投资研究 Agent

Q2.1 – Q2.13 · 13 题 · 13 张

Q2.1用一分钟讲清 Folio 做了什么。›
他在测什么

能不能把复杂系统压成一句话。压不出来的人，通常自己也没想清楚。

照着说
「Folio 是一个装在电脑上的投资研究工作台。用户选一只股票发起研究，它自己排计划，去取行情、财务、新闻这些数据，先把数据存下来，再让模型只根据存下来的东西写一份研究报告，报告的每一节都挂着来源，能翻回是哪一次调用、什么时候取的。」
「它和『聊天框加一个查股票接口』最大的差别是顺序：我们是先取证、再写；聊天机器人是边查边写。所以三个月后用户问『当时为什么看多』，我们能翻出当时那份数据。」
「规模上大概二十项数据能力、十三个技能包、八十六条评测用例。」
这是什么

一句话：把「查资料—写报告」这条人工流程，改成一条有留痕的流水线。

它是桌面应用，不是网页服务——模型调用、数据落盘、报告存储都在本机，所以没有账号体系也没有服务器，代价是每台机器要自己配数据密钥。

记三个词就够：先取数、再综合、留证据。

他要追的话
  • 「本地优先是什么意思？」模型调用、数据落盘、报告存储都在你这台机器上，不依赖中心服务。收益是研究过程和结论不出本机；代价是每台机器自己配凭据、自己管数据。
红线
  • 不要一开口就报七个包名、monorepo 结构。这些是问到再说的细节，不是开场白。
Q2.2它和『聊天机器人套一层股票数据』到底差在哪？›
他在测什么

你有没有抓住这个系统的本质。答「我们功能更多」是零分，答出机制差异才是满分。

照着说
「差三步。第一步，取证和写作分开：我们先把这一轮要查的全查完、冻结存下来，然后才让模型写。写的时候工具是物理禁用的，它只能读已经存下的事实。聊天机器人是边查边写，查到什么写什么。」
「第二步，缺失会如实留下：某一项取数失败，整轮研究不会失败，它会变成报告里的一条『不可用』。这听着像容错，其实是可信度问题——『没有评级数据』和『干脆不提评级』是两件事。」
「第三步，每节都能回查：报告里每节挂着证据，能力 id、运行 id、取得时间、摘要、标的。用户三个月后回来问，能翻到当时那一次调用。」
这是什么

聊天机器人是边查边写，我们是先查完、冻结、再写。多这一步，换来的是「报告里每句话都能对上一份数据」。

代价很直接：数据可能已经过时——所以每条证据必须记取数时间，这一条不能省。

他要追的话
  • 「为什么不直接边查边写？体验还更连贯。」两个理由：①取证写作交织时，中途一次工具失败会让已写好的段落失去依据，而报告已经生成，改不回去；②只有冻结数据，「只依据已保存事实」这句话才可验证——不冻结，你没法证明模型写的时候没偷偷再查一次。
红线
  • 不要说「我们用了 Deep Research 所以更强」。Deep Research 是个名字，不是机制。
Q2.3你说上下文是十段拼起来的，为什么是这个顺序？能换吗？›
他在测什么

你是背下了这个顺序，还是想清楚了「谁说了算」。这一问的追问会一直追到「哪两段绝对不能换」。

照着说
「能换，但有两处是硬的：规矩必须在数据前面，用户的问题必须在最后。因为模型读到什么就按什么干——先看到规矩，它会照着规矩看数据；先看到数据，它会先自由发挥，再拿规矩给自己找补。问题放最后，是因为模型对末尾最敏感。」
「中间几段是环境：当前工作区、语言、有哪些技能、上次查的是哪只股票。这里只有一处我认为不能动——工作区必须在『上次查的标的』之前，因为用户可能站在 A 股页面问 B 股，当下的视角优先。」
「这一条我自己得说清：它是我从两类状态的生命周期推出来的，代码里没写理由，也没有测试守着。所以它是设计意图，不是被保证的行为。」
这是什么

所谓「装配」，就是每轮请求前，把散在系统各处的状态按固定顺序拼成一段文本喂给模型。拼的不是措辞，是「这一轮模型必须知道什么」。

十段里前三段是常量（角色纪律、答案格式、外部内容定性），中间是环境快照，最后是用户这句话。空段落会被自动过滤掉，所以有些段是可选的。

记这一句：规矩在前、环境在中、问题在后。

他要追的话
  • 「第 6 到第 9 段能换吗？」能。唯一不肯动的是工作区在最近标的之前，而这条只是设计意图——没测试守着，重排数组不会红。
  • 「工作区为什么不写进会话记录、下轮从磁盘读？」会污染：三个月后回到这个会话，历史每轮都写着当时看的标的，模型会以为你还在看那只。也会失效：切了标的，磁盘还是旧值。
  • 「技能只放目录、不放正文，模型压根不读怎么办？」会，它可能真的不读。 目录只给 id、最多 160 字描述和就绪状态，然后要求它用工具去读正文。收益是十三个技能包不爆上下文；代价是多一次往返，而且可能不发生。这只能靠评测度量，不能靠提示词喊得更大声。
红线
  • 不要说「因为这样效果最好」。没做过对比实验就说效果，是自曝。
  • 不要背成「第一段角色、第二段契约、第三段……」，那是复述，不是理解。
Q2.4上下文不就是拼 prompt 吗？›
他在测什么

你对这活儿有没有轻视。答「是拼」的人，会被认为只会写提示词。

照着说
「是拼字符串，这点我认。但拼的不是措辞，是信息结构——哪些状态有资格进这一轮、按什么优先级、缺了会怎样。这三件事决定模型的知识边界。」
「排查『答非所问』的时候，第一步永远是看这一层的输出，不是改措辞。模型不知道你说的是哪只股票，你把提示词改出花来也没用，因为那个信息根本没到达。」
「它还是链路里最便宜也最贵的环节：实现便宜，但它每轮都跑，任何一处多余都按轮次放大成 token 成本和注意力稀释。」
这是什么

prompt 管「你怎么说话」，上下文管「你看到了什么」。改措辞解决表达问题，改上下文解决信息问题。

判断方法很简单：把这次改动撤掉，模型是「话说得不一样」还是「知道的事不一样」。前者是 prompt，后者是 context。

他要追的话
  • 「那你怎么保证改提示词不会改坏？」三条单元测试钉住：传了工作区，prompt 里必须出现标的和视图，并且必须含那句指代消解指令；没传，prompt 里不能出现这一段；传了技能中心，必须出现技能目录。意义不在测试本身，在于把「提示词」变成了可以被断言的对象。
红线
  • 不要说「提示词工程就是玄学」。说这话的人，通常没写过能回归的提示词。
Q2.5一个 Agent 为什么需要能力注册表？直接调接口不行吗？›
他在测什么

你有没有想过「权限的物理边界」这件事。这是从「会写 Agent」到「敢上生产」的分水岭。

照着说
「不行。因为『直接调接口』意味着模型能碰到什么，由它自己决定，而它不是可靠的边界执行者。」
「我们在系统提示词里写了『只用注册过的工具』『不要自己拼券商命令行』，但这句话不构成约束——模型想调什么还是能调。真正兜住的是注册表：模型能看到的工具名就是注册表里那二十个，别的一个入口都没有。」
「一句话：提示词是意图，注册表是执行。它还有两个身份：同一份声明同时服务模型和工作流；它也是溯源的起点——报告里每条证据的来源都产生在这里。」
这是什么

注册表就是一张「公司允许模型使用的能力清单」。一条能力声明九个字段：id、展示名、说明、分类、风险级别、授权类别、工具名、输入 schema、执行函数。

建表时挡三种错：id 格式不对、id 重复、工具名重复。建好之后只给查询接口（list / get / query），不给增删接口。

内部 id 是名词式的（market.quote），给模型看的工具名是动词式的（get_quote）——内部 id 改名会破坏已存的运行记录，所以两者必须分开。

他要追的话
  • 「注册表为什么只读？运行时热插拔不是更方便？」因为能力目录必须在启动时确定，否则评测不可复现——两次实验工具集不一样，分不清是模型变了还是工具变了。代价是加能力要重启。
  • 「就绪状态显示 ready，结果调用失败，这不算 bug 吗？」不算。ready 只比对技能声明的必需能力 id 在不在注册表里，不探网络、不查权限。ready 是刻意的弱保证，只代表「已注册」。三件事必须分开：已注册、已登录、这次调用成功。
红线
  • 不要说「加了注册表更安全」就完事。安全是结果，他要听的是机制。
Q2.6深度研究为什么要先落盘再综合？不能边查边写吗？›
他在测什么

你对「可审计」这件事的理解深度，以及你能不能说出取舍的代价落在谁身上。

照着说
「因为报告一旦生成，就必须对得上一组固定的依据。边查边写，中途一次工具失败就会让已经写好的段落没有依据，而报告已经发出去了。」
「我们的顺序是四步：先排计划，再并发取数——四个工作单元，单项二十秒超时；每项结果立刻落一次检查点；然后只用检查点里的事实综合；最后挂证据发布。」
「只有把数据冻结，『只依据已保存事实』这句话才是可验证的——不冻结，你没法证明模型写的时候没再偷偷查一次。代价是多一次落盘，而且数据可能过时，所以每条证据必须记取数时间。」
这是什么

先取证、再写作，跟办案一个道理：证物先封存，写报告时只能看封存的东西。

计划是一份固定的有序能力清单，完整十项。注册表里没有的能力保留为「不可用」，绝不静默删掉一个研究维度——少一个维度要让人看见。

报告 id 固定成 report-<runId>，配合检查点重放，同一轮不会生成两份报告。

他要追的话
  • 「十项里有一项挂了，整轮算失败吗？」不算，降级成「部分成功」，失败项以不可用状态进运行清单。收益是新闻挂了不该让估值和财务白跑；代价是「部分成功」这个状态变复杂，所有下游都得能处理不完整的报告——这是有意识的复杂度转移。
  • 「为什么不做一个动态规划器，让模型决定查什么？」两个理由：报告可比性（不同标的章节结构要一致才能对比）、可复现性（评测要能断言「必需能力是否被调用」）。代价是策略外的新需求必须改代码。
红线
  • 不要说「先落盘是为了防止模型胡说」。防止胡说靠的是工具禁用和证据挂接，落盘解决的是「依据能不能对上账」。
Q2.7综合阶段禁工具，禁写不就行了？为什么全禁？›
他在测什么

你有没有抓住「副作用」之外的另一层风险：依据漂移。

照着说
「因为真正的问题不是副作用，是依据会变。只禁写看起来合理，但忽略了读——综合阶段如果还能重新取数，报告引用的数据就可能跟落盘的检查点对不上，那『可回查』这件事就假了。」
「所以综合阶段是把全部工具置空，包括读文件、执行命令和写文件，一个都不留。实现是：综合前提示词里带一个哨兵标记，扩展在回合开始前检测到它，就把当前活动工具列表备份、置空；之后任何工具调用无条件返回阻止，结束时恢复。」
「这一层是整个链路里最可信的一层，因为它是唯一不需要模型听话的一层。」
这是什么

用代码禁，不靠模型自觉——提示词管不住的事，用工具列表管。

配套还有一条：综合阶段的提示词必须要求「缺什么就写什么」。工具禁了它补不了数据，只能如实声明缺失。这两处必须同时改：只禁不要求声明，模型会硬编；只要求声明不禁工具，模型会偷偷补数。

他要追的话
  • 「那综合的时候模型发现数据不够，怎么办？」如实声明缺失，写进报告——这正是上面那条配套要求。
红线
  • 不要答成「为了防止模型乱调工具」。乱调是行为问题，依据漂移是正确性问题，后者严重得多。
Q2.8报告里的引用，你怎么保证不是编的？›
他在测什么

你知不知道自己的能力边界。这一问的标准答案不是「我们保证不会编」，而是「我们保证什么、不保证什么」。

照着说
「引用不是模型写的，它编不出来；但它能挂错地方。这两句要一起说。」
「模型的输出里根本没有『引用』这个字段——它只交章节编号、摘要、立场、正文。引用是它写完以后由程序重建的：拿编号去查这一节对应的数据有没有真的取成功，成功才生成一条证据，带上工具名、运行编号、取得时间、标的。模型没有写引用的入口，所以它写不出一个不存在的编号。」
「但它能挂错：编号是它自己填的。把『估值』那节的编号填成『财务』，系统就会生成一条真实但不相干的引用——引用本身真，指向错。」
「还有一件系统不管：正文里的数字，不逐个核验。」
这是什么

一句话分工：模型负责写内容，系统负责贴来源。 两边都不越界，所以来源不会凭空产生。

三个边界要能同时说清：来源假不假（编不了，机制保证）；来源和内容对不对得上（答不了，章节键是模型选的）；数字对不对（答不了，不逐个核验）。

他要追的话
  • 「那这段没引用的分析，不就是模型编的？」一半对。 数字能在已保存的取数结果里找到，是推理；找不到，就是我拦不住的编。我唯一能保证的是它没法拿假引用冒充依据。至于为什么允许没引用的节——强制每节都挂引用，会逼模型把不相干的调用挂上去，挂错比留空更坏。
红线
  • 绝对不要说「我们保证每句话都有引用」。一说这句，面试官下一步就会问「怎么保证」，然后你就得现编。
Q2.912 个确定性评测器具体测什么？为什么分数方向要统一？›
他在测什么

你是在「堆指标」还是在「设计度量」。堆指标的人答不出「方向统一」这四个字的意义。

照着说
「十二个确定性评测器就是十二个纯函数：读一次运行记录，算出一个分数。不调模型，同一份记录跑两遍结果一样。」
「分四组：运行有没有正常结束、该调的工具有没有出现；参数格式对不对、次数有没有超；成功调用有没有返回真数据、带没带来源；最新数据在不在时间窗里、出错后有没有补。」
「它只证明『有依据』，不证明『依据对』。（用例要求查苹果报价，调一次拿到 100 块、答案写 110，依据那项照样满分。）」
「方向必须统一：延迟和失败次数越低越好，汇总却要求越高越好。失败率换成『一减失败比』，延迟按六十秒递减。不统一，0.9 和 120 平均成 60。」
这是什么

类型层一共定义了 17 个指标：12 个确定性 + 4 个模型评审 + 1 个轨迹。但实际只注册那 12 个确定性评测器；模型评审要另外传 Judge 客户端才注册。所以「17 个都测了」这句话是错的。

它在项目里干的活：当唯一不靠模型的裁判。模型评审会偏、会飘；确定性评测只读运行记录，守住「工具调没调、参数填没填对、有没有依据」这些结构性底线。它测不了「说得好不好」，那部分只能交给评审模型。

指标它到底查什么它查不到
task_completion运行结束，且答案非空答案对不对
tool_recall预期能力名出现在调用里顺序对不对、调了几次
argument_validity参数符合 schema日期区间符不符合用户意图
max_tool_calls总调用数没超限花没花超预算
evidence_presence有成功调用返回非空数据答案里的数字对不对
provenance_presence调用带提供方和获取时间提供方可不可信
freshness_compliance最新相关调用在时间窗内每条新闻是否都够新
failure_recovery出现后续成功调用或重试措辞靠英文关键词匹配，换个说法就误判
他要追的话
  • 「为什么不全部用模型评审？」不稳定（同输入不同分）、贵，而且会掩盖结构性问题——工具没调、参数填错，纯函数一查就知道。代价是确定性指标只能测「结构对不对」，测不了「说得对不对」，所以模型评审那四个维度仍然必要。两类不是替代关系，是分工关系。
  • 「那到底注册了几个？类型层定义了 17 个吧？」类型层 17 个，默认只注册 12 个确定性评测器。这个差别必须主动说，否则被问到「17 个都测了？」，怎么答都是错的。
红线
  • 不要说「我们覆盖了 12 个维度」。维度是分组的说法，指标是个数，混着说会被追问到细节。
Q2.10评测跑出 92 分，能说明这个 Agent 好吗？›
他在测什么

你会不会被数字骗。这是评测岗最基础的一道筛子。

照着说
「不能。三个原因，一个比一个具体。」
「一，它不是通过率，那是单次运行的分数，不是一批运行里通过的比例。二，它来自评审模型，评审模型和被测模型可能有同源偏差，自己评自己那类问题它看不见。三，分母没说清：多少条样本、黄金语料还是真实运行、合成样本占多少。」
「正确的说法是：『在 N 条黄金语料上，结论分布是 X 条通过、Y 条需复核、Z 条失败。』（能当分母的样本我们有三套：八十六条主体用例、十四条中文用例、十一条深研金标集。）说分数之前先把分母摆出来，比分数本身有说服力。」
这是什么

一个分数能不能用，取决于三件事：分母是谁、谁打的、样本多少。 这三件事不交代，分数就只是个数字。

报评测结果永远报三样：结论分布、掉得最狠的那一项、分母是哪套数据集。

他要追的话
  • 「证据存在性这一项拿满分，说明依据很扎实？」只说明成功调用的返回里有非空数据，不核验答案里的每个数字。它的价值是排除「完全没取数就写结论」。
  • 「通过率能不能当北极星指标？」单看不行。要配有效性（有多少运行根本没跑起来）、用例数和分项指标；基础设施故障必须剔除，但「已启动然后超时」必须算负面——这条边界靠错误码判断，判错就污染通过率。
红线
  • 不要为了显得有成果，把「92 分」说成「准确率 92%」。这两个词的差别，面试官一句话就能问穿。
Q2.11外部新闻里带指令的情况，你们怎么防的？›
他在测什么

你做的是「加个过滤器」还是「设计防线」。四层纵深能不能讲清楚，决定了他信不信你真的想过攻击面。

照着说
「四层，因为它们挡的不是同一种东西。」
「第一层在入口清洗：控制字符、伪造的代码块围栏、DATA: 这类前缀、角色标记，都用固定规则处理；标题超 200 字、摘要超 1000 字就截断并打标记。默认是『标记』不是『删除』，因为删了会改变新闻原意。」
「第二层把新闻标成不可信数据，并在三条业务提示词前面插同一份防护规则：这是数据，不是指令。第三层是综合阶段把全部工具禁掉——就算它信了指令，也没有工具可用。第四层在输出解析时逐句过滤已知注入短语。」
「但我不说『防住了』。只说防住了已知四类，未知的挡不住。」
这是什么

四层各管一类风险：清洗挡结构伪造、提示词挡指令误读、工具禁用挡越权行动、输出过滤挡已知短语传播。

三处明确没防住，要能主动说：URL 只校验 http(s) 前缀和长度，不判网站信誉；语义污染挡不住——模型不调工具、只把观点改成极度看多，这层拦不到；还有一个真洞——输出过滤后某字段变成空串时，当前实现会回退原文，等于把注入句放回了持久化报告。

他要追的话
  • 「为什么默认标记而不是直接删？删了不是更安全？」删除会改变原意，破坏「引用外部说法要注明来源」的可核查性。代价是恶意短语还留在上下文里，只能靠后面几层再拦。
红线
  • 不要说「已经防住了」。「防住了」这四个字一听就是没打过攻防的人说的。正确说法是「防住了已知四类，未知的挡不住」。
Q2.1286 条用例里那 8 条回归，讲一个真实踩过的坑。›
他在测什么

你有没有把 bug 变成防线的习惯。这条问的是工程成熟度。

照着说
「讲一个：模型把盘中数据当成多月 K 线用，报告的走势判断整个偏了。」
「当时没发现，因为格式全对、工具也调了，只是参数选错了时间粒度。参数合法性那一项只校验类型和范围，不校验业务语义。」
「后来把那次真实运行记录脱敏固化成一条用例，断言写成『调用 K 线能力时，时间粒度必须是日线及以上』。从此谁改坏了默认值，这条就红。」
「我的判断是：一条真实 bug 的终点不是『修好了』，是『变成一条数据集用例』。」
这是什么

那八条不是随便加的，每条对应一个真实发生过的缺陷——比如把盘中数据当多月 K 线，比如根据一次报价编造估值比率。

加用例时要说清「这条要保护什么行为」，并且升数据集版本，否则分数不可比。

他要追的话
  • 「8 条够吗？」不够，而且我知道不够。八条只覆盖「发生过、且能被机械断言」的缺陷；「发生过但只能靠语义判断」的进模型评审。这个分类本身是取舍：能断言的进确定性门禁，断言不了的进评审，两边都不进的就会出现盲区。
红线
  • 不要编一个听起来很厉害的 bug。真实的小 bug 讲得细，比虚构的大 bug 可信得多。
Q2.13如果只能改一处，你改哪里？›
他在测什么

技术判断力，以及你会不会为了显得全面而不敢取舍。

照着说
「我会把单条 prompt 字符串改成 messages 数组。」
「现在系统约束、用户数据、输出契约全挤在一段文本里，只能靠顺序表达优先级。换成 messages，才真正能分层。」
「它是另外两个改进的前提：加记忆召回、加压缩，上下文里的块只会更多，靠一条字符串的顺序维持优先级会撑不住。先把分层做出来，后面两个才有地方装。」
「代价不小：运行时接口要从『收一条字符串』改成『收一个数组』，上游拼装、下游日志和追踪都要跟着改。所以现在是『知道该做、但排在后面』，不是『没想到』。」
这是什么

三个候选各有一个代价：加记忆召回要多维护一条链路、多一个可能失败的环节；加压缩会丢细节，而且丢哪些不可控；换 messages 要改接口和上下游。选第三个，因为它是另外两个的地基。

他要追的话
  • 「换 messages 要动什么？」运行时接口、上游拼装、下游日志与追踪，全都要改一遍。
红线
  • 不要说「我觉得现在这样就挺好」。这道题就是在测你敢不敢承认系统有演进空间。

三、CRM：跨境客户经营

Q3.1 – Q3.14 · 14 题 · 14 张

Q3.1用一分钟讲清这个 CRM 里的 Agent 在干什么。›
他在测什么

不是问你系统有哪些模块，是问你它一天在替谁做什么事。答成架构介绍就是零分。

照着说
「它替销售干一件最费时间的事：把一个客户散在三处的信息对起来——聊天记录、商机停在哪个阶段、公司资料里这类客户该怎么处理。汇成一份带来源的摘要，停手，让人判断。」
「比如客户问过一项服务就没动静了，销售问『这个商机为什么停滞』。它交出来的东西必须分三类：最近一次联系是几号，是读到的事实；『可能还在比价格』是推断，要单独标出来；没资料的部分直接说缺，不能把推断写成事实。」
「所以它只做三件事：读、标、停。对客户有影响的动作不做——四个内置 Agent 都没有直接发送工具，发消息、改商机要走正式操作和人工确认。」
这是什么

这套系统里有四个内置 Agent：情报、销售运营、客户沟通、监督。名字代表任务侧重，不代表权限一样——每个能看到的工具和范围是各自配的。

两个容易误会的地方，说清反而加分：

它不是聊天机器人。 每次提交都是一次独立的运行，请求不会自动带上全部聊天历史。要延续客户背景，得靠显式给的范围和已确认的记忆。

一个绿点不等于整件事办成了。 「运行完成」只表示这次跑到了终点；「评测待复核」表示质量还有问题；「消息行创建成功」也不代表外部平台已经送达。这三件事要分开看。

他要追的话
  • 「为什么说『受治理』？普通 Agent 不也有限制？」区别在限制写在哪。写在提示词里的是意图，写在工具装配、类型系统、数据库约束里的才是执行。三处都有落点：可见工具集由注册表决定，专家子 Agent 在类型层面无法声明写效果，副作用前有一条 SQL 同时校验队列租约和运行状态。
  • 「四个内置 Agent 权限一样吗？」不一样。名称只说明它偏重哪类任务，读写范围各自配——情报员能查联系人、商机、会话、知识、组织记忆，但它的契约要求把「数据库事实」和「推断」分开写。
  • 「每次提问会带上次的聊天记录吗？」不会自动带。页面会显示先前轮次，但每次提交创建独立运行，历史不会整段塞进去。要延续背景，得显式给客户范围或依赖已确认的记忆。
  • 「运行完成是不是就代表这件事办成了？」不代表。要看评测结论，还要看外部动作有没有真的落地——这三个状态是三件事。
红线
  • 不要说「我们在 CRM 上加了 AI」。这句话里没有任何工程信息。
Q3.263 个工具全挂给模型吗？›
他在测什么

你有没有意识到「工具太多」本身就是个失败源，以及「不给」这件事要做几步。

照着说
「不全挂。而且『不挂』要做两件事，不是一件。」
「第一件，按这个 Agent 自己配的白名单筛一遍。这里有两种不同的『不给』：效果分类不明的工具，根本不暴露给模型；对客发消息、请求人工接管这类外部动作，工具照给，但调用之后只生成一条待审提案，人点头才真执行。」
「第二件更容易漏：工具从工具集里摘掉的时候，提示词里提到它的那句话也要一起删。我们踩过——有个工具只清了描述、名字还留在常驻提示里，模型照样去调一个不存在的东西，白花一步。」
「所以判据只有一个：工具集变了，提示块跟着变。」
补充提醒
「子 Agent 那边是同一个思路：工具集是父级允许的和它自己声明的取交集，再用只读标志构造——它连『声明一个写工具』这条路都没有。」
这是什么

63 是工具总数，不是一次请求里模型看到的数量。

裁两刀：装配时（按这个 Agent 的白名单，效果分类不明的直接不暴露），子 Agent 启动时（父级允许的交集它自己声明的，再套只读标志）。注意「不给」有两种：不给工具，和给了工具但执行要人点头——对客发消息属于后者。裁完之后还有一个隐性动作——把提示词里对那批工具的引用同步删掉，否则等于把「不存在的工具」又念给模型听了一遍。

他要追的话
  • 「工具多了不是应该更灵活吗？」工具本身不是免费的，每个工具的描述都占上下文，而且工具越多模型选错概率越高。所以「装哪些」是个真问题，不是把所有能力塞进去就完事。
  • 「工具从工具集删了，提示词里还提它一嘴不行吗？」不行，这一点是实测出来的。有个工具（crm_list_webhook_sources）当初只清了描述、没清名字，泄漏又回来了：模型会去调一个已经不存在的工具，白花一步，错误还指不到根上。所以撤销工具时，工具名和提示词引用必须一起删。
  • 「子 Agent 的工具集是怎么定的？」父级允许的工具集和它自己声明的取交集，再用只读标志构造。也就是说子 Agent 连「声明一个写工具」这条路都没有——写死在类型里。
红线
  • 不要说「我们有 63 个工具所以能力很强」。63 是工具面宽度，不是能力强度；这两件事在面试里要分开说。
Q3.3模型填了个全零 UUID，你们怎么发现的？›
他在测什么

你有没有处理过「技术全绿、业务全错」这类最难查的故障。这题答得漂亮，能直接把评价抬一档。

照着说
「一个客户想约周四，参数都对，两次调用都成功，但客户就是没约上。」
「根因是模型碰到可选的 UUID 字段（记录编号）、不知道填什么时，不会省略，而是填全零那串——约定用它表示『空』，格式合法，校验拦不住。我们那句『值为空就用默认』只处理空值，它就穿过去了。系统按这个 id 查可约时段，查不到，返回零个——客户面前就是一个没有任何时间可选的日历。」
「修法不在出事那个函数里补判断。目录里有 28 个字段都接受缺省 UUID，逐个修等于按实例修，第 29 个还会从范围外长出来。所以清洗放在工具边界的统一入口，一次覆盖 28 个。」
补充提醒
「格式完全正确、但内容是模型瞎编的 UUID，不在这层洗——它跟真实 id 在这一层区分不出来，处理它的正确位置是『没找到这条记录』那个具名结果。」
「未知的哨兵值只能靠兜底，不靠穷举：把已知形态列成清洗规则，再保证任何查不到都走一条显式失败。」
这是什么

这类故障最坑的地方：每一层都返回成功，只有业务结果是错的。 查它不能看报错，只能看业务痕迹。

「成功」这个词在这类系统里有三层意思，必须分开：调用返回成功 → 业务真的做到 → 外部真的送达。 这个事故里第一层是真的，后两层是假的。

顺手把两个词说清。UUID 是数据库里每条记录的身份证——一串 36 位字符；全零那串是行业里约定用来表示「空」的写法，格式完全合法，所以校验拦不住它。handler 是工具背后真正干活的那个函数：模型只说「我要调这个工具，参数是这些」，校验参数、查库、写库都是 handler 在做——所以「在边界清洗」的意思是，在参数进入 handler 之前就洗干净。

一句话记住：「合法」不等于「有意义」。 全零 UUID 合法，但它指的不是任何一个真实对象。

他要追的话
  • 「那你怎么知道还有别的哨兵值？」不知道全部。能做的是把已知的哨兵形态列成清洗规则，并且在「没找到记录」这条路径上给一个具名结果——让未知的哨兵值至少能走到一个显式的失败，而不是静默查空。未知的东西只能靠兜底，不靠穷举。
  • 「为什么不在出事的那个 handler 上补一句？」因为错的不是那一个 handler。目录里 28 个接受缺省的 UUID 字段共享同一个假设——「不填就是没填」。逐个修等于按实例修，修完 28 个，第 29 个新字段还会从范围外长出来。所以清洗必须放在边界那个统一入口。
  • 「那这 28 个字段你怎么确认都覆盖到了？」靠位置，不靠盘点：只要它们都从同一个入口进出，清洗就必然经过。真正要守的是「新字段别绕过这个入口」，这是代码评审要盯的点。
红线
  • 不要把这个事故讲成「模型很笨」。模型行为没错，错的是接口契约没规定「不知道该填什么时该怎么表达」。
Q3.4工具出错为什么不抛异常，要返回一段话？›
他在测什么

你懂不懂 Agent 和传统后端的差别：异常会中断思考，一句话能让它换个角度。

照着说
「传统后端里工具出错就抛异常，调用链断掉，前端报错。但在 Agent 里，异常会让模型重试、或者直接放弃这一轮。」
「所以『这个客户不在你的范围里』这种情况，我们返回的是一段给模型看的话，不是 500。模型看到这句话，可以换个范围继续干活；看到异常，它只会说『抱歉我没能完成』。」
「但有一条硬约束：数据库层的错误必须抛，不能吞掉换成一个空数组。吞掉之后模型会拿空数组去推理，得出『这个客户没有商机』——技术上没报错、业务上完全错误。所以分界是：业务规则不允许的，返回话；技术故障的，必须抛。」
这是什么

区别在于这条错误对模型有没有意义：

权限不够、不在范围、状态不允许——这些是「系统在对模型说话」，它有用，能指导下一步。

数据库连不上、SQL 报错——这是故障，模型拿它没用，还会被误导。

代价是错误处理不再有单一出口，得靠审计日志判断真实成败。用路径复杂换模型可用。

他要追的话
  • 「那你们怎么区分这两类？」看是谁的判断：业务规则不允许，返回话；故障，抛出来。分界线不是「是不是错误」，是「这个结果对模型有没有意义」。
  • 「返回给模型的那段话，怎么写才算有用？」要写三件事：发生了什么（不在你负责的范围内）、还能怎么办（换一个范围，或者请客户经理授权）、需不需要人接手。只写「操作失败」，模型只能放弃。
红线
  • 不要说「我们都用 try-catch 兜住了」。兜住和吞掉是两件事，后者是这类系统里最贵的一种错。
Q3.5上下文里那个检查点为什么要放最前面？放最前面不会盖过客户刚说的话吗？›
他在测什么

你有没有意识到「位置即权威」这个模型行为特性。这题的追问会直接打到「那你怎么办」。

照着说
「会。而且这正是要解决的问题。」
「检查点是上一回合结束时的快照，比客户刚发的消息还旧；而模型会把越靠前的内容读成越权威的指令。放最前面，它就会压过客户刚说的话。」
「那为什么还放最前面？因为它必须被读到。放最后，模型会把它当补充信息；放最前，它才会被当成『这一回合的起点状态』。」
「关键是块开头那一句声明——『这是上一回合客户发下一条消息之前写的，如果下面的历史已经回答了它，以历史为准』。不是让模型自己判断新旧，是显式告诉它优先级。」
这是什么

模型有个很稳定的习惯：越靠前的内容，它越当指令；越靠后的，它越当信息。

所以「重要的放前面」和「新的事实说了算」是冲突的。这套设计的解法不是调顺序，是在块里写一句冲突裁决规则——位置给注意力，声明给优先级，两件事分开办。

他要追的话
  • 「那 System prompt 呢？历史里那条旧的还在吗？」会被替换。历史里第一条 system 消息会被当前这一轮的 systemPrompt 覆盖。理由是业务策略改了之后，旧 prompt 不能继续生效，否则模型同时收到两套矛盾规则。代价是模型不知道策略改过——但对一个要对外说话的 Agent，「知道策略演变」不如「只遵守当前策略」重要。
  • 「这些顺序有测试守着吗？」没有，这是要主动承认的缺口。上下文装配目前没有断言级别的保护，全靠注释和代码评审。哪天有人重排数组，测试不会红。
  • 「检查点里到底存了什么？」存的是这一回合已经跑完的东西：每项能力的结果和状态（成功、失败、不可用），加上运行本身的状态；再往后要续跑，还要靠服务端那份私有的完整消息快照，那份不给界面读。
  • 「恢复会不会多出第二次运行？」不会，但靠的不是什么 id 派生。运行 id 在入口就生成一次，队列工单按它去重；已经收尾的运行被重新领到工单时，handler 一看状态不再是排队或运行中就直接返回，不会再启动一遍。
红线
  • 不要说「放最前面因为最重要」。它恰恰不是最重要的，它是最旧的——能讲清这个反直觉，这题才算答对。
Q3.6用户点了取消，为什么还要两道保障？›
他在测什么

你对「取消」这件事的时序理解，以及你知不知道自己为什么要加第二道。答成「加了 abortController 就解决了」的，是没想过写库那一段；答成「我们有两道，一道是……另一道是……」的，是在背配置，没答因果。

照着说
「因为『取消』这两个字，在两个时刻意思不一样：请求还在飞的时候，取消是掐断它；数据已经开始往库里写的时候，取消挡不住——写进去就撤不回来，只能拦在写之前。」
「一道机制只能覆盖一个时刻。掐断那段靠看门狗，800 毫秒轮询一次运行状态，读到取消就 abort 当前请求；拦写那段靠每个副作用执行前的一条 SQL，同时校验队列租约和运行状态，不通过这个副作用整体不做。」
「所以不是我们喜欢加两道，是单道一定留窗口。取消不是『按停止键』，是『先把数据库状态改掉，再让每一笔写入动手前先看一眼这个状态』。」
这是什么

单道为什么会漏，看时序就清楚：

请求还在飞——掐断它。abortController 覆盖这一段。

模型已经返回、代码正在写——拦在写之前，因为写进去就撤不回来。abortController 在这一段已经没用了，它断不了已经发出、正在执行的那条 INSERT。

中间还有一个很短的窗口：SQL 校验刚过、INSERT 还没落盘，取消到了。这一段两道都覆盖不到。

所以「两道」说的是两道防线，不是两道保险——两个时刻各需要一把锁，而这两把锁都锁不全中间那个瞬间，剩下的靠事后对账兜。少一道，就有一个窗口敞着。

他要追的话
  • 「第二道不也就是一条 SQL？凭什么信它？」因为它读的是数据库当前状态，而取消的第一动作就是改数据库。不是「通知到了没」，是「旗子改了没」——只要读到已取消，就一定生效；没读到，说明取消还没落库，那这一刻它本来就还没生效。数据库是唯一有权威的判断依据。
  • 「如果取消恰好发生在 SQL 通过之后、写库之前呢？」那就会真写进去，取消已经来不及拦了。这时系统把它标成「效果可能已完成」，然后去副作用本该留痕迹的地方查——客户消息表、外发表里有没有对应行。查到就补齐状态，认下这笔已经发生的事；查不到就按取消收尾，这一步不再做——用户要的是「别做」，不是「补做」。查不清（比如外部接口根本不提供查询、本地也没记）才交人工核对，人工是最后一道，不是第一道。
  • 「那『查不到就重新执行』是什么时候用的？」那是恢复路径，不是取消路径。进程崩了、断网重开、租约被别人接手、人工点重试，这些场景下系统的意图是「把活干完」，所以查到就跳过、查不到才重做。两条路共用「查痕迹」这一个动作，因为判断「到底做没做」的方法一样；但查完往哪走方向相反：取消路径查不到要收手，恢复路径查不到要动手。判据只有一条——这次到底有没有「不要做」的意图。
  • 「为什么光看运行状态不够，还要校验队列租约？」租约防的是另一类重：原来那个 worker 掉线、任务被另一个接手，两个都在跑同一个副作用。此时运行状态还是「运行中」，但写的已经不是同一个人了。租约确认「这一笔还归我」，运行状态确认「这个活还没被取消」，两个条件缺一个都不能写。
红线
  • 不要答成「我们加了 abortController 就解决了」，也不要答成「取消就是停止」——前者没想过写库那一段，后者把两个时刻混成一个。另外两处容易说错的：别把「写完了去对账」说成第三道保障，它不是防，是承认防不住之后的补救；也别把「查不到就重新执行」套到取消场景上——用户点了取消还说「重新执行一遍」，等于自相矛盾，那条只属于恢复路径。
Q3.7三个专家并行，成本不就翻三倍了？你们怎么控？›
他在测什么

你会不会把一个「看起来很酷」的能力，做成一个「成本失控」的负债。

照着说
「先认账：收益是三路并行、能互相校验，代价也是三倍起——token 三倍、延迟取最慢的那个、三份观察要合并成一条结论，还有并发写的问题。」
「我们做的不是『把成本降下来』，是让这笔代价可控、有上限、失败可见。每条约束对着一种具体的失控：十八次共享工具额度，防三个专家放开了查；每个专家三回合，防某一个陷入循环偷烧预算；百分之五十五留给专家，防协作把父流程的钱吃光、父流程自己没钱做总结；九十秒超时，防一个慢的拖住整个运行。」
「判断一套并发控制好不好，就看它能不能回答一句：最坏情况下花多少。」
补充提醒
「实现上不是三个专家各开一个循环，而是开一个固定大小的 worker 池，三个任务进同一个列表、用共享游标去取，额度检查跨专家共享一个计数器。好处是额度只记一次账、并发上限是常量、某个专家挂了不占名额。」
这是什么

多 Agent 的成本问题不是「三倍」，是「三倍且不可预测」。所以这套设计的重点是把不可预测变成有上限。

判断一套并发控制好不好，看它能不能回答一句：最坏情况下花多少？ 这里有三个天花板：额度、回合、预算，任意一个先到就停。

他要追的话
  • 「为什么不按专家均分额度？各给六次不是更公平？」因为需求不一样：事实分析员可能两次就查完，政策顾问需要八次。均分的结果是前者浪费四次、后者不够用。共享池让能力强的多用、弱的少用，总额度不变。这个取舍选的是「成本确定性」而不是「公平性」。
  • 「这几个数字怎么定出来的？」先认性质：是写死的常量，一套值对所有客户，没按组织规模或客户复杂度区分。定值走的是反推，不是正推——先定一单最多花多少、最多等多久（九十秒），再倒算次数：十八次是三个专家共享的工具入口总数，按三路各查一遍的量级估；每个专家三回合，等于留两轮查证加一轮收口；五十五分给专家，四十五留给父流程汇总，因为父流程没钱收口整单就白跑。但要诚实：这套值当初没留推导记录，也没做敏感性测试，十八改成二十四会怎样我没数据。要补就从运行事件表回看分布——多少任务在额度内完成、多少顶到上限、顶到上限的那批是不是本来就注定失败；顶到上限还能成功，说明额度太紧；从来没触及，说明虚高。
  • 「固定大小的 worker 池，比三个专家各开一个循环好在哪？」三点：额度只记一次账（一个计数器），并发上限是常量（不会因为加专家就压垮下游），某个专家挂了不占着名额。三个独立循环这三件都要各记一遍，很容易记漏。
红线
  • 不要说「这些数字是调优出来的」。没做过对比实验就说调优，追问一句「那优的定义是什么」就崩了。
Q3.8三个专家，两个说 500 万、一个说 600 万，你们投什么票？›
他在测什么

你对「多数投票」这种看似合理的机制有没有警惕。这是这一节最能拉开差距的一题。

照着说
「不投票。冲突作为结构化数据上报给父流程，由它呈现给人。」
「因为投票在这件事上是错的：三个专家里有两个看的是同一个工具返回——它们的票不独立。如果那个工具本身返回了过期数据，两票投出来的还是过期数据，而投票机制还给了它一个『多数通过』的假权威。」
「正确做法是让销售看到分歧、自己去核实，而不是系统替他选一个。在这个业务里，替人判断事实的代价，远高于让人多看一眼。」
这是什么

投票成立的前提是每个投票人独立。三个专家共用同一批工具、同一份资料，独立性根本不成立——所以「两票对一票」只是听起来像民主。

而且这个策略是显式声明的：冲突不会让父流程自动合并掉，而是浮出来交给人。但边界要说清——它只能发现进入结构化材料的差异（同一字段不同值、或版本不同），报告里那些语义层面的前后矛盾，它看不出来。

他要追的话
  • 「那两个数不一样，一定是冲突吗？」不止一种可能，系统分三型：同一资源同一字段给出不同值，是事实分歧；某个专家失败或超时，是专家失败；哈希不同但版本字段不同，是资料在跑的过程中改版了。第三型最难也最有价值——两个分析员看到不同金额，可能一个看到的是旧版本，这不是分歧，是时序问题。
  • 「那这五个字段之外的呢？」分不出来，这是已知缺口。字段不在列表里，改版就会被误判成事实分歧。做法是把这个列表当常量维护，新增字段时同步加进来——靠约定，不靠机制。
  • 「分歧上报之后，界面上怎么呈现？」按三型分开呈现，不合并成一条「金额不一致」。因为事实分歧要人去核对、专家失败要重跑、资料改版要重新取数——三种处置方式完全不同，混在一起就只剩一句「有冲突」。
红线
  • 不要说「我们做了加权投票」或「我们取置信度最高的那个」。这两种答法都会引出「权重怎么定」「置信度怎么来的」两个你答不了的问题。
Q3.9证据为什么只存哈希，不存原值？后面用起来不是更麻烦？›
他在测什么

你知不知道「比对」和「读取」需要的信息量根本不一样。这题的追问会打到一个具体的规范化坑上。

照着说
「三个专家各自去读库，回来交两样：一份可定位的材料（哪份政策第几段），一份对某个字段的断言（『这个商机的金额是多少』）。」
「断言里不存原值，只存一个取值指纹和一个值类型。因为冲突检测只需要『相不相等』，不需要『是多少』；而且这些记录会进事件日志和主管能看到的元数据，原值一进去，等于把客户字段又抄一份到别处。」
「坑在规范化：算指纹前，对象的键和数组都要排序。不排序，同一个值换个字段顺序就是两个指纹，两个专家读到一样的东西也会被判冲突。时间戳要从指纹里跳过。」
「代价是父流程要数值时得回去重查一次；好处是取数绕不开权限校验。」
补充提醒
「碰撞在 SHA-256 上不是现实风险。真正的风险是同一份数据走了两条序列化路径——所以规范化只认一个函数，所有调用方共用它。」
这是什么

哈希在这里的用途不是防泄露，是「只知道相不相等，不知道是什么」——这个性质刚好够判断冲突，又不够泄露内容。

所以它不是安全措施，是一个刻意减少信息量的设计：需要判断时给你判断，需要内容时让你回去查。原文的定性更准：隐私和可比性同时成立的折中。

他要追的话
  • 「哈希怎么算？为什么不能直接用普通哈希？」规范化之后再哈希：标量直接序列化，数组排序后拼接，对象按键名排序后拼接，最后 SHA-256。排序是必需的——不排序，「a 在前」和「b 在前」的同一个对象哈希会不同，两个专家明明看到同一个东西，也会被判成冲突。
  • 「两个不同字段碰巧哈希相同怎么办？」碰撞在 SHA-256 上不是现实风险。真正的风险是规范化不一致——同一份数据走了两条序列化路径。所以规范化只认一个函数，所有调用方共用它。
  • 「父流程真要用具体数值时怎么办？」按「资源类型 + 字段名」回去重新查一次。这一次查询走的是正常读取路径，有权限和范围校验——这也正是存哈希的好处：取数必须经过受控路径，不会因为「证据里存过」而绕开检查。
  • 「既然只要比相不相等，为什么不直接比字符串？」因为要「规范化之后比」才有意义：100000 和 100000.0 字符串不同但语义相同，键序不同的同一个对象字符串也不同。哈希只是把规范化后的结果钉成一个固定长度的值，让比较变成一次纯粹的相等判断。
红线
  • 不要说「哈希是为了安全」一句话就完。他要听的是为什么在「进父事件日志」和「给主管读的元数据」这两个场景下不能存原值——不是怕被人偷，是本来就不该流到那儿去。
Q3.10知识检索里，你怎么区分『库里没有』和『有但不够像』？›
他在测什么

你有没有处理过「否定性结果」这个坑。这是 RAG 里最容易做错、也最少人意识到的地方。

照着说
「这两种情况到达提问者时长得一样，都是『没查到』，但它们要求的动作完全相反——一个是去找人，一个是换个问法。系统要是分不清，就永远给不出正确建议。」
「所以检索返回里除了过关的片段，还带回一个最高相似度——即使没过阈值也返回。有了这个数字，才能判断是『完全没有』还是『有相近但不够像』。」
「还有一个工程取舍：阈值不写在数据库函数里，检索时传一个等于不过滤的值，拿到结果后在应用层筛。因为阈值是产品策略、会随知识库质量调整，写在数据库函数里，改一次要发一次迁移。」
这是什么

「没找到」是一句无用的话——它没告诉你下一步该干什么。

所以这套设计的重点是：无论结果好不好，都带回一个「有多接近」的数字。有了它，才能把「没有」拆成「真没有」和「不够像」。

他要追的话
  • 「那溯源呢？怎么知道引用的是哪个版本？」每条片段带回三件套：版本 id、段落位置、内容指纹。这里有个特别容易被混淆的地方：版本 id 是「被观察的索引的身份」，不是「这条政策现在还有效」的批准——索引版本只说明它在哪份数据里，不说明它没过期。
  • 「那过期引用怎么办？」这是要承认的缺口。三件套目前用于「证明来源」，没有用于「阻止过期引用」。要做到后者，需要在检索之后、展示之前再做一次版本有效性检查，这一步在当前实现里不是强制的。
  • 「最高相似度低于多少，才该说『库里没有』？」0.4。它是余弦相似度（1 减距离），常量是 LIMIAR_PADRAO = 0.4，与数据库从 0097 迁移起的默认值一致。这里有个容易被绕过的点：没有第二条判定线，过滤线和判定线是同一条。一个片段都没过 0.4 时，那个「最好但被淘汰」的分数本身就是答案——0.38 说明库里有接近的但不够好，0.05 说明根本没这条，两者要求的动作相反。0.4 是工程默认值，不是标定出来的，我不假装它是；真要标定，办法是拿一批已知「库里有」和「库里没有」的问题，分别跑出最高相似度的分布，取能把两组分得最开的那条线——这件事我没做过。
红线
  • 不要说「我们用向量检索所以很准」。准不准和能不能溯源是两件事。也不要被「阈值多少」问住之后用「这是产品判断」把数字糊过去——先给数，再给它的身份（默认值还是标定值），最后才谈可调。
Q3.11客户记忆为什么不让外部记忆服务当权威？›
他在测什么

你分不分得清「记忆」和「事实」这两个词。答成「外部服务不可靠所以要兜底」只答了可用性，没答到区别。

照着说
「那个服务是带模型判断的记忆服务：丢一段进去，它自己决定记不记、要不要合并，给你的不是原文。客户记忆在我们这边是人工确认过的事实，一行一条存在自己库里，谁确认的、第几版、内容指纹都在。」
「区别三点：谁写的——一个自己推断，一个只在人确认后才写；写的是什么——一个是对客户的理解，一个是客户的原话；能不能翻账——它那条改了只剩『现在是这样』，我们那条能翻回谁确认的。」
「所以它不能当权威：客户改主意时它只能回答『它认为他想要什么』，承诺出事说不清谁确认的。我们只让它干排序——正文不进答案，只拿顺序排我们的记录，它挂了退回本地顺序。」
补充提醒
「检索回来还要逐条核对四个东西：客户作用域、本地那一行、记忆作用域、内容指纹。四个全中才有资格参与排序，全中也不等于采信它的正文。」
「写之前先探测接口支不支持『禁掉推断』这个开关，不支持就不发——老版本会静默丢掉参数，然后自己推理出几条，那就不是客户说的话了。」
「同步超时状态判『未知』：至少等 60 秒，只做列举不做新增。状态不明时贸然新增会产生重复记忆，而重复记忆会被检索加权，等于一条客户偏好被算了两次。」
这是什么

「记忆」这个词在两个地方指的不是一回事：一个是客户说过的话的记录，一个是某个服务对客户的印象。

印象可以拿来排序——哪条更相关，往前放。记录不能外包，因为它得答得出「谁、在什么时候、确认了什么」。印象没有责任人，记录有。

这两件事一旦混起来，出问题时分不清是客户改主意了，还是模型改主意了。

他要追的话
  • 「超时了怎么办？不知道远端到底写没写进去。」状态判为「未知」，然后走人工核对：至少等 60 秒，而且只做列举不做新增。因为状态不明时贸然新增会产生重复记忆，而重复记忆会被检索加权，等于一条客户偏好被算了两次。
  • 「那刚写入的记忆，立刻检索能查到吗？」不保证。同步是异步的，这是最终一致的代价，不是缺陷。但文档和界面不说明，用户会觉得「我明明刚确认过」。
  • 「这四个条件为什么偏偏是这四个？」它们各挡一类错：客户作用域挡「这是别人的客户」，本地那一行挡「这是另一条记录」，记忆作用域挡「同类但不同事」，内容哈希挡「内容被改过」。少任何一个，都会出现「看起来对、其实不是这一条」的命中。
  • 「四个都对上了，是不是就能直接用它给的原文？」不能。匹配只赋予「参与排序」的资格，正文仍然从本地那条记录重新读——它返回的文字始终不进答案。
  • 「既然它返回的字一个都不进答案，为什么还要同步过去？」因为它唯一的价值就是排序。本地最多取五十条候选、最终只留十条，靠它给相关度先排一遍；不同步过去，它就没有东西可排。代价是最终一致——刚确认的那条，马上查不一定能查到。这是有意识付的运维成本，不是缺陷。
红线
  • 不要说「我们接了 Mem0 所以有记忆能力」。接了哪个服务不重要，重要的是你给了它多大权限。
Q3.12所有模型调用都走一个网关？预算是在什么时候判的？›
他在测什么

你知不知道「事前拦截」和「事后统计」的差别，以及这条拦截线上有没有旁路。

照着说
「先纠正题目里的假设：不是一个网关，是两条通路。一条管 embedding 这类辅助调用，另一条管所有 Agent 回合——后者在代码里叫唯一接缝，模型调用必须从这一个函数过。」
「预算就判在这条通路的入口：先解析这个组织用哪家模型、哪把密钥、预算多少，然后在发出第一个字节之前查一次本月已经花了多少，放行还是拒绝；跑完再把用量写回去。」
「卡在第一个字节之前，是因为钱在发出去那刻就产生了；判在后面只能记账，追不回已经花掉的钱。而只要有一个调用点自己新建客户端，它就绕过预算和审计——上限就变成建议了。」
补充提醒
「终止型错误：有个字段标记『这是永久性业务否决，不是系统故障』，告诉队列取消作业而不是记为失败。不这样标，一次超支会变成 N 个会话乘最大重试次数次重试，把唯一能解释原因的那条告警淹掉。」
「密钥三列落库（密文、初始向量、认证标签），解密只在实例化那一刻，不进提示词、不进工具返回、不进日志；不可用原因分五种具名，因为处置完全不同。」
【队列领任务 → 先装上下文（第7步）→ 调模型之前先过网关，网关在发出请求前判断预算（第8步）→ 模型开始运行→ 发起调用工具请求】
这是什么

两条通路这个设计值得记：管 embedding 的和管 Agent 回合的，本来就不是一套，连密钥来源都不共享——改一边不要想当然另一边跟着变。

关于预算只有一句话：能在花之前拦住，才叫上限；只能在花之后算出来，那叫报表。

他要追的话
  • 「那个『终止型错误』是什么？为什么它特殊？」有个字段标记「这是永久性业务否决，不是系统故障」，它告诉队列应该取消作业而不是记为失败。因为按普通失败处理，一次超支会变成「N 个会话 × 最大重试次数」次重试，每次都产生一条最高级别告警，把那条唯一能解释原因的超支告警淹掉。
  • 「那有没有故意不设这个标记的错误？」有，理由正好相反。有一类错误是「组织配了自己的地址却用了安装级密钥」，它故意不是终止型——因为没有配套的人工接管兜底，取消了就是「对话没有回复，也没有人接手」。所以宁可走普通重试，等运维在重试窗口里修好配置。同一个字段，两组相反的取值，因为「取消之后谁来收尾」的答案不一样。
  • 「为什么要用客户自带密钥？」三个后果：成本记在客户自己的账上，密钥泄露面留在客户那一侧，平台不代持别人的长期凭据。代价是每个组织都要配一次，配错的表现还很像故障（——所以凭据不可用的原因才要分五种。）
  • 「那界面上的余额和实际拦截会不会对不上？」不会，因为查钱只有一个函数，界面读的和拦截读的是同一个，一个尺子量两次。
红线
  • 不要说「我们做了 token 统计」。统计是观测，拦截才是控制。也不要说「所有调用都走一个网关」却说不出两条通路的区别——那说明这两个词是从别处背来的。
Q3.13评测为什么两个结论要取更严的？取平均不是更合理？›
他在测什么

你对「两个度量源可靠性不对称」这件事的判断。

照着说
「不合理，因为两个源的错误方向不对称。」
「确定性门禁给一个结论——通过、需复核、失败、未运行；语义评审给一个结论加一个分数。合并时结论取更严的，分数取更低的。」
「语义评审是一个模型的主观判断，它会错在『太宽松』这个方向；确定性门禁是机械判定，它错的空间小得多。取平均等于允许一个模型的乐观判断，去抵消一次机械判定的失败。」
「一句话收口：永远不会因为一个模型的乐观判断，放过一个有确定性缺陷的运行。」
这是什么

平均的前提是两个东西误差方向对称——一个偏高一个偏低，平均才有意义。

这里不对称：机械判定基本不会「误放过」，模型评审会。所以平均不是「折中」，是拿一个松的结论去稀释一个严的结论。

他要追的话
  • 「那语义评审挂了怎么办？整个评测算失败吗？」不算。分情况：原本「通过」的降成「需复核」，原本更严的不变，状态记为「评审失败」并记下错误类型。这个降级规则是单边、非对称的——只降「通过」。因为「确定性说通过、但评审没跑起来」等于有一道门没检查，不能声称通过；而「确定性说失败」的时候，评审跑不跑都不影响结论。
  • 「为什么先跑确定性，不先跑评审？」因为确定性门禁可能直接判「未运行」——没有可评的东西，这时候提前返回，不调评审模型。省一次调用，也避免用语义分去填补一个空结论。
  • 「两个都通过的时候，分数还有用吗？」有用，但只用来观察趋势，不用来判定。分数适合看「这一版比上一版好还是差」，不适合回答「这一次能不能上线」——后者的答案必须是结论，不是分数。
红线
  • 不要说「两个都测所以更全面」。全面不是理由，方向不对称才是理由。
Q3.14可观测为什么用白名单不用黑名单？trace id 为什么不用随机 UUID？›
他在测什么

两个小设计背后是不是同一个思路：默认保守。

照着说
「白名单这条路，属性的键是一个封闭清单，只允许十几个固定名字，之外的直接校验失败。想新加一个字段出去，必须改这个清单，改动会被代码评审看到。黑名单正好相反——想不到的字段会自动流出去。」
「trace id 用哈希不用随机：从确定的输入算出来，同一个运行不管投递几次、在哪个进程投递，id 都一样，重试不会多出一条重复的 trace。」
「这两个设计其实是同一个思路：默认不放行，只放明确允许的。白名单是『想不到的字段默认留下』，哈希 id 是『同一次运行永远同一个身份』——都在压缩『意外』这两个字的空间。」
补充提醒
「span 名也受约束：只允许五个固定名字，不符合命名规则的一律改成『已脱敏』，防止用户可控的字符串混进去。」
「投递走独立的事件通道，不和主队列共用。外部服务会慢、会挂，共用的话一次超时就会拖住客户的对话——这是隔离失败域。」
这是什么

三个设计其实是同一个思路：默认不放行，只放明确允许的。

白名单是「想不到的字段默认留下」，哈希 trace id 是「同一次运行永远同一个身份」。它们都在减少「意外」这两个字的出现空间。

他要追的话
  • 「为什么说『只有第三层能证明成功』？」一次投递要拿到三层确认：本地排队了、对端 HTTP 说接受了、远端能回读到。HTTP 200 只证明对方收到请求，不证明它存下来了。只有回读能证明数据真的到了。
  • 「那导出里会带客户正文吗？」不会，投影时排除客户正文、工具入参、模型的隐藏推理和任何凭据。SQL 里留的是规范事实，可观测平台里留的是便于查询的副本——两边职责分开，出事时以 SQL 为准。
  • 「白名单要新增一个字段，流程是什么？」改那个枚举，然后过一个会看见它的代码评审。这个麻烦是刻意的：加字段这件事必须有人同意，而不是谁 prop 里带个字段就自动流出去。代价就是每加一个字段都要改代码——但这正是它挡得住意外字段的原因。
红线
  • 不要说「我们做了脱敏」。脱敏是结果，白名单枚举是机制。

四、跨项目：把两个项目打通

Q4.1 – Q4.8 · 8 题 · 8 张

Q4.1两个项目都在做上下文装配，做法差在哪？为什么不一样？›
他在测什么

你会不会把一套做法无脑套到所有场景。

照着说
「共同点是都在解决同一件事：把散在系统各处的状态，装配成一次模型调用能用的上下文，都按固定顺序编排，都对可选段做了缺失兜底。」
「最要紧的差异是：一个解决『信息有没有到达』，一个解决『新旧冲突谁说了算』。前者的典型故障是模型不知道用户在说哪只股票；后者的典型故障是过时的检查点压过客户刚说的话。」
「判断是：形态差异由运行时接口决定，不是设计偏好；冲突处理由业务性质决定——研究场景里上一轮结论和这一轮新数据不会互相覆盖，客户对话里旧快照和新消息天天打架。」
补充提醒
「形态上一个是一条 prompt 字符串、靠顺序表达优先级，一个是分块的 messages 加一块独立 system prompt。」
「两边可以共用『按顺序拼装 + 可选段过滤』那层骨架，但冲突裁决那一段是业务特有的，必须各自实现。硬合会把对话侧的优先级规则带进研究侧，多一层没人维护的规则。」
这是什么

两个系统喂给模型的东西，本质都是「这一轮它必须知道什么」。差别不在拼法，在这批状态里有没有互相矛盾的。

研究任务的输入是「数据」，数据之间不打架，只可能缺；对话任务的输入是「进程」，上一秒和这一秒会打架——所以那边要额外解决「谁说了算」。

他要追的话
  • 「那哪个更难？」处理冲突更难。信息缺失会表现成「答非所问」，容易被发现；冲突处理错了，系统照常返回 200，模型照常输出一段通顺的话，只是内容是错的，什么痕迹都没有。
  • 「那两边能共用一套装配代码吗？」不能直接共用，但可以共用「按顺序拼装 + 可选段过滤」那层骨架；冲突裁决那一段是业务特有的，必须各自实现。硬合会把对话侧的优先级声明带进研究侧，反而多一层没人维护的规则。
红线
  • 不要说「两个差不多」。差不多的回答等于没回答。
Q4.2Folio 的能力注册表和 CRM 的 MCP 工具，本质区别是什么？›
他在测什么

你对「工具契约」这个概念的理解是不是只有一个模板。

照着说
「共同点是都把外部能力收敛成一套给模型用的契约，都在边界上做参数和身份校验，都要求调用结果能溯源。」
「差异在服务对象：一个的契约同时服务模型和工作流——模型看文本和参数约束，工作流看结构化数据和来源；另一个同时服务外部 AI 客户端和自家 Agent，共用同一份实现，避免同一个问题对人说一个答案、对 AI 说另一个。」
「治理重心也不同：一个重在能力半径——哪些能力存在、就绪怎么算、缺了怎么降级；另一个重在权限半径——这个人能看到哪些客户、这次运行范围是什么、哪些动作必须人工确认。研究型工具怕取到错数据，业务型工具怕做错动作。」
这是什么

一个管「你能拿到什么」，一个管「你能动什么」。读错和做错，是两种完全不同的事故。

读错可以重读，做错撤不回来——所以业务侧必须多一层「人点头」。

他要追的话
  • 「那你自己更认可哪种设计？」我更认可 CRM 那套，因为它能迁移出去。 「效果四分类 + 未知默认按最严处理」是一套判断框架，任何有副作用的系统都能套。Folio 那套「就绪只是弱保证」是个好洞察，但它解决的是一个界面的诚实问题，换个场景就用不上。代价是 CRM 那套重：每个动作都要分类、要人点头，自动化的比例天然上不去。（顺带说清：Folio 那套我更愿意讲，因为它反直觉；但「更愿意讲」不等于「更认可」。）
  • 「那如果让你把 CRM 那套搬到 Folio，会动哪？」先动工具声明——把风险级别和授权类别加上，再把「未知默认按最严」接进综合阶段。装配层不用动，因为研究侧的读取本身没有副作用。
红线
  • 不要背概念差异（MCP 是协议、注册表是模式）。他要听的是治理重心。
Q4.3两个项目都做评测，思路差在哪？›
他在测什么

你会不会把评测当成「跑个分」。

照着说
「共同点是都先确定性、后语义，两层结论合并；都把基础设施故障和任务质量失败分开；都用版本化数据集保证分数可比。」
「差异在粒度。一个是十二个评测器加三套数据集，八十六条主体、十四条中文、十一条金标，是『广度铺开』；一个是确定性门禁加一个四维语义评审，是『单条运行走深』。」
「合并策略也不同：一个把指标统一成越高越好再聚合，适合一批运行横向比；一个直接取更严的结论、取更低的分数，适合一次运行纵向判。」
「判断：这两套不是竞争关系，是两种评测粒度。做版本对比需要可聚合的分数，做上线门禁需要不可协商的结论。」
这是什么

一个回答「这一版比上一版好还是差」，一个回答「这一次能不能放上线」。

横向比要的是可比性（所以要把所有指标拧成同一个方向再平均）；纵向判要的是不容商量（所以一个缺陷就否掉，不让平均糊弄过去）。

他要追的话
  • 「那如果只能用一套？」选「确定性 + 取更严」那一套做门禁，因为它不会因为模型的乐观判断放过有确定性缺陷的运行；另外补一套可聚合的分项分数做趋势，否则你永远不知道版本之间是变好还是变差。
  • 「两套评测的数字能放一起比吗？」不能。数据集、样本量、合并规则都不同，放一起比只能得出「谁的分母更大」。要比就各比各的趋势。
红线
  • 不要说「评测就是为了保证质量」。这句话没有信息量。
Q4.4你怎么定义『Agent 做对了』？›
他在测什么

这是整套方法论的总纲。答得好，前面所有题都会被重新解读成「他有一套体系」；答得散，前面就只是零散知识点。

照着说
「我分四层判，从硬到软。」
「第一层，动作对不对：该调的调了没有、参数合不合法。第二层，依据真不真：引用的东西有没有在工具返回里真的出现过、来源能不能回溯到某一次调用。这两层都能机械断言，但第二层要区分『有依据』和『依据对』。」
「第三层，话说不说得清：切不切题、事实撑不撑得住、缺材料敢不敢说、结论能不能执行。这层只能靠评审模型，也必须承认它主观。第四层，知不知道自己不知道——说『查不到』合格，说『大概 30 倍』不合格，走的是一条不可复现的路。」
「所以我判做对了是四层都过，不是最后一层看着不错——最后一层最好看，也最不可靠。」
这是什么

这四层其实是「错的代价从低到高」排的：工具调错能重跑，依据假了能重查，话说不清人还能判断，而「不知道却编得像知道」是最危险的——它让人失去警觉。

四层都对应能算的东西：工具召回、参数合法性、证据存在性、来源完整性、四个语义维度、失败恢复。讲不出对应的指标，就等于没测。

他要追的话
  • 「那第四层怎么测？」测「声明缺失」的比例和准确度：该声明的时候有没有声明，不该声明的时候有没有乱声明。前者漏了是「编」，后者多了是「怂」，两个方向都要测。
  • 「四层里哪一层最容易做到假达标？」第二层。证据存在性只要「有非空数据」就满分，很容易看起来很好——但答案里的数字对不对，它不管。所以第二层必须配人工复核或更细的断言。
红线
  • 不要答成「输出质量高就是做对了」。这是这道题的反面答案。
Q4.5这两个项目里，哪些设计是必须的，哪些是锦上添花？›
他在测什么

取舍能力。答「都必要」等于没有判断。

照着说
「必须的三条：工具契约——没有它模型能碰到不该碰的东西；依据先落盘——没有它报告不可回查；人工确认边界——没有它一次误判就是对客事故。这三条去掉任意一条，系统就不能上生产。」
「锦上添花的两条：渐进式披露，技能只放目录——它优化的是上下文成本和注意力，但全量注入也能跑；多 Agent 协作——它提升分析深度和速度，单 Agent 顺序做完也能出结果，只是慢和浅。」
「判断标准一句话：去掉之后，系统的失败会不会伤到系统外部？会，就是必须的；只影响内部效率和体验，就是优化项。」
这是什么

「必须」和「锦上添花」的界线不在技术难度，在失败会不会溢出到系统外。

报告写错、消息发错，是外部看得见的损失；上下文多花点钱、慢一点，是自己扛的。

他要追的话
  • 「那多 Agent 那套并发控制，算必须还是锦上添花？」协作本身是优化项，但一旦决定做协作，并发控制就是必须的——不做的话三个 Agent 会互相覆盖、重复干活、成本失控。这是「可选能力」和「该能力的必要配套」的区别。
  • 「如果砍掉一个必须项来换工期，你砍哪个？」不砍必须项，砍范围——把「所有对客动作」缩成「只做只读分析」。砍必须项是拿事故换工期；砍范围是拿功能换工期，后者可逆。
红线
  • 不要说「每个设计都是必要的」。这句话会让面试官怀疑你没做过取舍。
Q4.6如果上下文窗口涨到 1M，你这些设计哪些会作废？›
他在测什么

你是在「应对当前限制」还是在「设计正确结构」。这题在测你有没有想过自己方案的前提。

照着说
「会松动的是两类：渐进式披露的必要性下降，技能正文可以直接塞进去；历史裁剪和压缩的紧迫性下降，长会话不用急着压。」
「不会变的是核心问题：遗忘不是问题，冲突才是。窗口再大，也解决不了『上一轮的结论和这一轮的新事实谁更权威』，也解决不了『模型有没有看到它该看的那一段』。」
「还有一个反向观点：窗口变大反而让『选择性注入』更重要。因为注意力是有限的，不是窗口有限——把一百万字塞进去，模型对中间部分的回忆会明显下降。所以『放什么进去』不会因为窗口变大而消失，只会从『塞不下』变成『塞了也白塞』。」
这是什么

窗口解决的是「装得下吗」，解决不了「看得见吗」和「听谁的」。

装得下是存储问题，看得见是注意力问题，听谁是权威问题。 后两个跟窗口大小无关。

他要追的话
  • 「那你会怎么验证『塞了也白塞』？」做一组对照：同一个问题，一次只给相关段落，一次给全量文档，看答案质量差异。这类实验用现有评测体系就能跑，不需要新工具。
  • 「那 1M 窗口下，你的评测会怎么变？」加一条「中间段落召回」的对照用例：同一份长材料，把关键事实分别放开头、中间、结尾各测一次，看答案还命中不命中。窗口变大不会让这条消失，只会让它更必要。
红线
  • 不要说「窗口大了就不需要上下文工程了」。这句话会暴露你没想过注意力和窗口是两件事。
Q4.7你最大的技术判断失误是什么？›
他在测什么

自省能力，以及你会不会为了面子编一个「假失误」。

照着说
「早期我认为工具出错就该抛异常——程序里本来都是这么写的。」
「后来发现模型会把异常理解成『这条路不通』，然后放弃整个任务，而不是换条路。它不重试，它会道歉。更糟的是有些框架会把异常兜住、返回一个空结果，模型拿着空气编出一个看起来挺合理的答案——你连错都发现不了。」
「所以我把整层的错误处理改了：错误只要能写成模型看得懂的一句话——比如『主源超时，可以换备用源』——就返回一段话；只有真正的故障才抛。判断标准就一条：这条错误，模型读完之后能不能做出下一个动作。」
「现在我的标准是：每个结论，我都要能说出用什么证据可以反驳它。」
补充提醒
「另两个可替换的例子：把模型自报的置信度当成可信分数（那个数是它自己说的，和正确率没有稳定关系）；评测只看总分不看分项（总分涨了，没测的那部分可能正在变差）。」
这是什么

这题考的不是失误大小，是你有没有真的改过做法。

结构固定四步：当时怎么想的 → 做了什么 → 后果是什么 → 现在会怎么想。 缺了最后一步，就变成了讲故事。

他要追的话
  • 「那你后来怎么避免同类问题？」给机制，不给决心。三选一：「给结论加一条必须同时写明的边界」「把这类判断做成一条可断言的用例」「在文档里显式标注哪些是推断、哪些是实测」。
  • //「这三个失误里，哪个代价最大？」第三个——前两个是认知错误，改过来就好；第三个是方//法错误，它让你以为自己在变好。所以我现在先看分项和失败模式，再看总分。
红线
  • 不要说「我最大的失误是太追求完美」。这是回避，不是回答。
Q4.8如果让你重做一个，你会怎么设计？›
他在测什么

你有没有从这两个项目里沉淀出可复用的结构，而不是每次从零想。

照着说
「骨架不变，还是四层：契约层管工具与权限，装配层管上下文与记忆，编排层管阶段与恢复，验证层管评测与观测。骨架不随项目变。」
「变的是三个业务参数：业务语义、副作用边界、失败代价——研究对客户经营，出报告对发消息，答案不准对动作做错。」
「如果要说一处具体改进：我会把『上下文装配』和『评测断言』从一开始就绑在一起。两个项目都是先做装配、后补评测，结果装配的设计理由只写在注释里，没有测试守着。正确顺序是先定下『这一轮模型必须看到哪几段』，把它写成断言，再实现装配。」
「所以重做的核心不是换技术栈，是把可验证提前到设计阶段。」
这是什么

这题在看你有没有「模板」。有模板的人讲层次，没模板的人讲功能。

而且他真正想听的是：你现在知道当初哪里做错了。所以必须给一处具体的顺序错误（这里是「先装配后评测」），不能只说「我会设计得更好」。

他要追的话
  • 「那会不会拖慢开发？」会，但代价在别处。先写断言花的时间，比后期排查「为什么模型答非所问」花的时间少；而且断言本身就是设计文档——面试官问「为什么这个顺序不能动」，答案就在断言里。
  • 「先写断言，断言写错了怎么办？」断言也会错，所以要写清「这条断言保护的是哪个行为」。行为变了就改断言，而不是改代码去迁就它。真正危险的是没人知道断言为什么在那儿。
红线
  • 不要说「我会用更好的框架」。框架不解决问题结构。

五、技术地基：一定会被问的基础题

Q5.1 – Q5.10 · 10 题 · 10 张

Q5.1MCP 到底是什么？和 Function Calling 什么关系？›
他在测什么

你会不会把一个协议当成一个概念来背。

照着说
「MCP 是一套把外部系统能力统一暴露给模型的协议——相当于给工具定了一套统一的说明书格式：叫什么、参数什么形状、返回什么结构。」
「跟 Function Calling 是两层：Function Calling 是模型侧的能力，能输出『我要调哪个、参数是什么』；MCP 是工具侧的约定，工具长什么样、怎么被发现、怎么被调用。一个管模型会不会用，一个管工具怎么描述出来。」
「项目落点：CRM 里六十三个客户经营能力全按 MCP 声明，好处是同一份实现既能被外部 AI 客户端调用，也能被自家 Agent 在运行时调用，不用维护两套。」
这是什么

打个比方：Function Calling 是「会打电话」，MCP 是「电话簿的格式标准」。

模型天生会「我要调某某工具」这个动作，但工具怎么登记、怎么让别人发现，是另一件事。没有统一格式，每家客户端都要单独适配一遍。

他要追的话
  • 「那自己定义一套工具格式不行吗？」行，只要不打算被别人用。用协议的好处是同一个工具对不同客户端都成立，代价是要守协议的表达能力边界——有些复杂参数结构表达起来会别扭。这是生态取舍，不是技术优劣。
  • 「MCP 的工具有状态吗？」协议本身不管状态，状态留在实现里。CRM 那边每次调用都带组织、身份、范围，等于把「谁在什么上下文里调」当成参数传进去——工具不记「上次谁调过我」。
红线
  • 不要把 MCP 说成「一个框架」或「一个 SDK」。它是协议。
Q5.2Function Calling 底层到底发生了什么？›
他在测什么

这是最基础也最能筛人的一题。答错的人，后面所有「工具治理」的讲解都站不住。

照着说
「先纠正最常见的一个误解：模型不执行函数。它输出的是一段意图——我要调这个名字的工具，参数是这段 JSON。」
「完整回路四步：模型输出意图，你的代码解析并执行，结果作为一条新消息塞回去，模型基于它继续说话或者继续调工具。这是单次 Function Calling 的执行流程；反复迭代这个流程，才构成 Agent Loop。」
「一个推论，这句最重要：所以『模型能做什么』完全由你挂了多少工具决定。这就是为什么两个项目都要做工具装配和注册表——它是物理边界，不是提示词里的建议。」
「还有一个失败模式：模型会编工具名、会填不存在的参数、会拿哨兵值占位。所以边界上必须有 schema 校验和清洗。」
这是什么

模型全程只有一件事：读文本，吐文本。 它吐出来的是「我想调 get_quote，参数是 AAPL」，真正去请求券商的是你的代码。

所以「模型很危险」这件事，实际取决于你给了它几个可以调的东西——它连自己执行的能力都没有，所谓危险都是你挂上去的。

他要追的话
  • 「那模型怎么知道有哪些工具？」工具列表在每次请求里跟着上下文一起发过去，所以工具描述本身就是提示词的一部分——描述写得含糊，模型就选错工具。这也是「工具名要用动词」的原因。
  • 「模型一次能并行调多个工具吗？」能，但并行意味着它同时押注几个假设。只读工具没风险；有副作用的工具必须在边界上串行化或加锁，否则两个并发写会互相覆盖。
红线
  • 不要说「模型自己调用接口」。这一句就把底层的理解暴露了。
Q5.3RAG 的完整链路，每一环可能出什么错？›
他在测什么

你会不会把 RAG 当成「向量库 + 检索」两个词。

照着说
「我习惯按七个环节拆，但真正容易出事的是三个。」
「一是分块。按固定长度硬切，会把一句话切成两半，检索回来的就是半句，模型只能猜。所以按文档本身的结构切，不按字数切。」
「二是否定性结果。库里有相近内容但不够好，和库里头压根没有，到用户这儿长得一样，都是『没查到』——但补救动作是相反的：一个该换个问法，一个该去找人。分不清，就会一直给错建议。」
「三是溯源。引用找不回原句，报告里那个数字就没法核。所以每条片段都带上传它的版本、位置和内容指纹。」
「一句话：RAG 难的不是检索准不准，是『检索不到的时候说什么』。」
补充提醒
「另外四环，被问到再补：索引版本没管会引用已废止的政策（做法是每次发布建新版本、移指针，不覆盖）；阈值和 top-K 拍脑袋（阈值放应用层，改策略不用发数据库迁移）；拼装超预算被硬截断（按类型定制，K 线留最后 60 项、新闻留前 10 条）；用户确认的事实没有回流（进了独立表，不进 RAG）。」
这是什么
环节典型错误项目里的做法
分块切断语义，检索到半句按结构切，不按固定长度硬切
索引版本没管，引用了已废止的政策每次发布建新版本、移动指针，不覆盖
检索阈值和 top-K 拍脑袋阈值放应用层不写进库函数，改策略不发迁移
否定性结果分不清「没有」和「不够像」即使不过阈值也返回最高相似度
溯源引用找不回来源每条片段带版本、位置、内容指纹
拼装超出预算被截断按类型定制截断（K 线留最后 60 项、新闻留前 10 条）
反馈用户确认的事实没有回流人工确认的偏好进独立表，不进 RAG

一句话理解：RAG 是「先挑出可能相关的几段，再让模型读」。 容易出问题的地方不是「挑得准不准」，是每个环节都在悄悄丢信息——切断了、版本旧了、截断了、没查到却不说。

他要追的话
  • 「为什么不把所有东西都塞进上下文，非要检索？」成本、延迟、注意力三个原因。但更重要的是可溯源——全文塞进去，模型引用时你没法知道它引的是哪一段；检索回来带位置和指纹，才能回查。
  • 「七环里哪一环最容易被忽略？」否定性结果。其余六环出问题都会「看起来不对」，只有它会安静地给出一个「没查到」，然后整条链正常往下走。
红线
  • 不要只讲「分块、向量化、检索、生成」四个词就停。这四个词谁都会背。
Q5.4为什么不微调？›
他在测什么

你会不会在「该用工程解决」的地方用「该用训练解决」的手段。

照着说
「因为这两个项目里的错，没有一类是微调能修的。」
「错分三类。一类在流程里：工具该不该禁用、预算超了怎么办、重试几次，模型表达得再好也修不掉。一类在供给：它把盘中数据当多月 K 线用，走势判断整个偏了，根子是没拿到『当前时间粒度』，补一句上下文就够。一类在术语：同一个领域词反复被理解错——这才是微调的主场，而这两个项目里占比很小。」
「还有个代价：微调之后可解释、可回归都会下降，出问题只能重训，不能改一行代码。而这两个项目要的恰恰是『能定位到哪一环』。」
「所以判据是：只有『同一个术语反复被理解错』且『提示词改不动』时，才轮到微调。」
这是什么

微调改的是「模型怎么说话」，不改「模型看到什么」和「流程怎么走」。

大部分 Agent 的 bug 属于后两类，所以微调打不中。 这就像打字总是错同一个字，该改的是输入法词库（上下文），不是重新学写字（训练）。

他要追的话
  • 「那什么时候你会选微调？」分类任务、固定格式抽取、需要极致延迟或成本的场景。判断标准是「这个错误能不能用规则和数据通路修」，不能才轮到训练。
  • 「如果只有表达类错误，你会微调吗？」先试三件事：把术语解释写进常量契约、给一两个示例、把输出契约收紧。三件都试过还错，才是微调的场——因为微调之后你失去了「改一行就回滚」的能力。
红线
  • 不要说「微调成本太高」。成本高不是理由，理由是这个错不该用训练来修。
Q5.5上下文长度和成本怎么权衡？›
他在测什么

你有没有把 token 当成一种真实预算来管。

照着说
「先拆成三个不同的量：单次请求的输入长度、一轮对话的累积长度、一个任务的工具调用轮次。这三个数量级完全不同，控制手段也不同。」
「对应三种手段：精简工具返回控单次，裁剪历史控累积，限制轮次和额度控轮次。」
「关键在一个设计原则：这三件事的触发时机不一样——一个在回合开始、一个在回合结束、一个在每次工具返回之后。做成一个函数，任何一处条件变化都会波及另外两处。」
「项目落点：预算判定放在请求发出之前，超支时一个 token 都没花；工具额度用共享计数器，跨子 Agent 共享，谁先抢到谁用。」
这是什么

「上下文太长」其实是三件不同的事，混在一起说就永远管不好：

这一句太长（单次）、这段对话太长（累积）、这个任务调太多次（轮次）。三种病，三副药。

他要追的话
  • 「那压缩历史会不会把关键信息压掉？」会。所以压缩只做「把长对话变成结构化摘要」，不做自由摘要——摘要字段是固定的（承诺、异议、下一步动作），这样至少知道丢了哪一类东西。
  • 「三个量里哪个最容易失控？」累积长度。单次和轮次都有硬上限，累积没有——会话可以一直长下去，而且每一轮都要把历史重新发一遍。
红线
  • 不要说「我们都是按需截断」。按需是最容易出事的做法。
Q5.6幂等在 Agent 系统里为什么特别重要？›
他在测什么

你有没有意识到 Agent 系统的重试是常态而不是异常。

照着说
「Agent 系统里重试是必然的：工具超时、模型返回中断、进程重启、网络抖动。普通系统重试一次读接口没事，这里重试一次可能就是给客户发了两条一样的消息。」
「Folio 那边有两个落点：报告编号由运行编号派生，检查点重放不会产生第二份报告；跟踪编号按确定输入算哈希，重试不会在监控平台多出一条重复记录。」
「CRM 那边有一个落点：对客消息用外部唯一键加确定性运行编号去重，重复投递撞在同一个键上。」
「更狠的一条：状态不确定时不重放，走核对——去该留痕迹的地方查，有就补状态，没有才重试。等于把幂等做成『不确定就不做』。」
这是什么

幂等就是「做一次和做十次，结果一样」。

普通系统里它是优化；在 Agent 系统里它是安全底线——因为 Agent 天然会重试（模型失败会再试、队列会重投），而它手里握着的是「给客户发消息」这类不可逆动作。

他要追的话
  • 「那如果核对也查不出来呢？」标成「效果可能已完成」，转人工。宁可多一次人工核对，不可重复执行一次不可逆动作。
  • 「幂等键怎么选才不会撞？」用「业务对象 id + 动作类型 + 确定的运行 id」，不要用时间戳或随机数——那等于没有幂等。撞了要能被发现，所以键要落库并带唯一约束。
红线
  • 不要说「加了唯一索引就幂等了」。唯一索引能防重复插入，防不住重复的对外动作。
Q5.7乐观锁和悲观锁，你各用在哪？›
他在测什么

你会不会在不该用锁的地方用锁。

照着说
「判据：冲突少、代价可控，用乐观锁，就是版本号，写时校验；冲突多、或者写本身很贵，用悲观锁，先占住。」
「乐观锁落在人工确认后写入：写的时候带上读到的版本号，对不上就拒绝。这里冲突来自两个人同时改同一个客户，概率低但必须发现。」
「悲观锁落在队列领任务：先咨询锁、再跳过已被别人锁住的行，一次领一批。这里多个 worker 抢同一批，冲突高频，领错了就是重复执行。」
「还有个易漏的：围栏令牌。一个 worker 领了任务后可能已经死了、租约还没过期，另一个抢到同一任务开始跑，这时前一个突然活过来要写结果——围栏令牌让它只能失败，不能赢。」
这是什么

区别在你什么时候付出代价：

乐观锁写的时候才发现冲突，代价是可能要重做一次；悲观锁一开始就占住，代价是别人等着。

所以选哪个看一件事：冲突多不多。 少就用乐观，多就用悲观。

他要追的话
  • 「围栏令牌和版本号有什么区别？」版本号防的是「数据被改过」，围栏令牌防的是「执行权已经被别人拿走」。前者管数据，后者管执行者。
  • 「乐观锁冲突了，直接报错吗？」不直接报错。先把最新版本读回来，判断这次的改动还成不成立；成立就带新版本重试一次，不成立才让人看。直接报错会把「别人改了个无关字段」变成一次失败。
红线
  • 不要说「我们用了行锁保证一致性」。行锁保证不了「谁有权写」。
Q5.8咨询锁和『跳过已锁行』是干什么的？›
他在测什么

你有没有真正写过并发消费，还是只用过现成的队列。

照着说
「问题是：多个 worker 同时从一张表里领任务，怎么保证同一个不会被两个人领走。这个项目的队列不挂外部服务，就建在数据库里。」
「两个机制各管一半。咨询锁保证『同一时刻只有一个进程在做抢占』，不用大家一起等；跳过已锁行保证『领的时候不排队』——被别人锁住的行直接跳过去找下一条，不等它释放。」
「合起来的效果：一批 worker 同时领活，各拿各的，谁也不等谁，也不会重复领。」
「补一个真实的运维参数：领到之后要写上谁领的、什么时候领的；十分钟以上的孤儿作业由回收机制放回队列；失败按二的尝试次数次方分钟退避，最多五次转成死信。」
这是什么

SELECT ... FOR UPDATE SKIP LOCKED 是 Postgres 里的一句话，字面意思就是「锁住这些行，但别人已经锁住的就跳过」。

它解决的问题是：一群人抢活的时候，不要排队。 排队会让吞吐掉到只剩一个 worker 在干活。

他要追的话
  • 「为什么放在数据库里做队列，不用现成的消息队列？」因为队列和业务数据在同一个事务里——「改业务状态」和「投递任务」能原子完成，不会出现「状态改了但任务没投出去」。代价是吞吐不如专用队列，但这类系统的量级不需要那个吞吐。
  • 「跳过已锁行会不会漏任务？」不会漏，只是这一轮跳过——被别人锁住的行在对方提交后自然可见。真正要防的是「锁住了但进程死了」，那是租约超时回收要解决的。
红线
  • 不要说「我们用的是消息队列」然后讲不出怎么保证不重复消费。
Q5.9流式输出怎么实现？断了怎么补？›
他在测什么

你有没有做过「长连接中途断开」这种一定会发生的场景。

照着说
「模型按增量返回文本和工具事件，服务端把它们翻译成几种统一事件——工具开始、文字增量、消息完成、运行完成，每条带自增序号，推给前端渲染。运行时是独立子进程，事件一行一条穿过进程边界回来，所以这一步翻译是必须的。」
「为什么序号是关键：有序号，断开重连才能按『最后收到第几号』补发缺口。没有序号，重连只能整轮重来。」
「还有个更重要的点：『收到完成事件』不等于『消息已经存盘』。这两件事必须分开，否则用户会看到消息显示了、刷新之后没了。」
「一个取舍：忙的时候直接拒绝，不排队。排队会让人等一个不知道多久的回复，拒绝至少让他知道现在发不了。」
这是什么

流式就是「模型吐一个字，前端显示一个字」。它带来的新问题是：连接可能会断，而用户已经看到了半句话。

解决靠两个东西：序号（知道断在哪）和落盘确认（知道什么真的存下来了）。

他要追的话
  • 「那如果补发的时候数据已经被清了呢？」按最后序号补不回来，就退化成整轮重取。所以保留窗口要够长，这是个参数问题，不是设计问题。
  • 「断线重连时，前端怎么知道从哪补？」靠它收到的最后一个序号。所以序号必须由服务端生成、单调递增，不能前端自己数——前端数的序号在丢包时会跟着错。
红线
  • 不要说「用了 SSE 就实现了流式」。SSE 是传输方式，不是可靠性方案。
Q5.10你简历上这些技术，哪些是会用、哪些是懂原理？›
他在测什么

自我评估的准确度。这一题答得保守一点，反而加分。

照着说
「我分三档说。」
「懂原理的，能讲清内部机制和失败模式：TypeScript 类型系统、Postgres 的锁与隔离级别、HTTP 与鉴权、事件驱动的基本模型。」
「会用的，能写能排错但没读过实现：React、Next.js、Redis、Docker、测试框架、可观测平台的接入。」
//「只读过没写过的，我坦白说：比如某个外部记忆服务的内部排序算法、某个协议的服务端实现。」
「只读过没写过的，主要是别人的基础设施层：记忆服务内部的召回排序、协议的服务端实现这一类。这类我知道它怎么工作、为什么这么设计，但没动过它的代码，不敢说『我改过』。」
「判断标准我给自己定的是：能讲清『它在什么情况下会坏』，算懂原理；只能讲清『怎么用』，算会用。」
这是什么

这一题在测你知不知道自己不知道。校招面试官对「精通」两个字的容忍度极低——因为一说精通，他就会问到实现层。

分三档不是谦虚，是自我保护：你把边界说了，他就不会拿你不知道的那块来打你。

他要追的话
  • 「那你怎么快速把『会用』变成『懂原理』？」读一次源码加一次故障排查。具体说：找一个真实报错，顺着栈读到根因，那一遍读下来比看十篇文档管用。
  • 「那你怎么知道自己哪一档判错了？」看追问的深度。他问「内部怎么实现」而你答不上，就说明你把「会用」说成了「懂原理」。当场纠正比提前吹更可信。
红线
  • 不要把简历上每个词都说成「精通」。校招面试官对「精通」两个字的容忍度极低。

Q6.1你技能里写了『业务 SOP 拆解为工作流』，具体怎么拆？›
他在测什么

这个词最容易注水，一百个人写，九十九个拆不出步骤。答得出拆法，这一栏才算真的。

照着说
「先说前提：不是所有 SOP 都该拆。拆的前提是步骤之间有确定的前后依赖，而且每一步的产出能被下一步直接消费。不满足这两条，拆了只是把一次调用变成五次。」
「拆法四步：列出人工现在的步骤；标出哪些步骤需要判断、哪些只是取数；给每一步定义输入和输出；找出哪几步能并行、哪几步必须串行且互斥。」
「项目落点：深度研究那条链就是这么拆的——计划确定查什么，模型不参与；取数交给工具，四路可并行；综合交给模型，必须串行而且工具被禁；发布交给工具，固定顺序。四段的划分依据不是『业务上有四个阶段』，而是『这四段的失败方式和恢复方式各不相同』。」
这是什么

对应技能栏：Agent 应用开发 · 业务 SOP 拆解为工作流

SOP 拆成工作流，本质是判断「这一步该由谁做」：需要判断的交给模型，只是取数的交给工具，不需要灵活性的写死。

判断错了就会出两种病：该工具的让模型做（不稳定、贵），该模型的写死成流程（一遇变化就崩）。

他要追的话
  • 「拆完发现某一步模型老做不对，怎么办？」按顺序排查三件事，别跳步：先看是不是上下文没给到（多数情况是这里），再看能不能把这步降级成工具，最后才考虑把这一步再拆细。一上来就加 Agent 是最贵的错。
  • 「拆成工作流之后，谁保证每一步真的按顺序跑？」编排层。每一步的产出是下一步的输入，类型上对不上就跑不下去——这比在提示词里写「请按顺序执行」可靠得多。
红线
  • 不要说「按业务流程一步步来」。这句话里没有拆法，只有复述。
Q6.2你说的『回合治理』，一个回合里你到底能插手几个地方？›
他在测什么

你在 Agent Loop 里是「使用者」还是「改造者」。只会调框架的人答不出插手点在哪。

照着说
「五个，按执行顺序排。但比数量更重要的是：它们全在模型外面。」
「发模型之前改上下文——压缩、裁剪，模型不知道你删了什么。工具执行前拦一道——这个动作该不该做、这次执行有没有资格，两个判断。回合结束前看该不该停——步数、成本、结果是不是已经交出去了。」
「还有两个更细的：把内部的消息格式翻译成模型认得的格式；工具执行完顺手把证据抠出来存下。」
「一句话收口：模型不配合也能生效。写在提示词里的是建议，挂在这些卡点上的才是约束。」
这是什么

对应技能栏：Agent 应用开发 · Agent Loop 与回合治理

一个回合不是「一问一答」，是模型说一句、要工具就执行、把结果塞回去、再问它，直到它不再要工具。

「治理」的意思是：在这个循环的五道口子上装闸门。装在模型外面的闸门，它绕不过去；写在提示词里的要求，它可以不听。

他要追的话
  • 「为什么不在提示词里写『最多调 5 次工具』？」因为那是建议。模型可以不遵守，而且不会告诉你它没遵守。次数上限必须由计数器在每次工具返回之后判断，超了就不再往下走——这个判断发生在模型之外，它管不着。
  • 「回合和轮数有什么区别？」一轮是「用户发一句到系统回一句」；一个回合是「模型说一句，可能要调几次工具」。一轮里可能有五个回合。（混着说会被追问到答不上来。）
  • 「五个插手点里，哪一个最容易写错？」第二个，工具执行前拦。它同时要判两件事：这个动作该不该做（业务），这次执行有没有资格（租约）。两件事写在一个 if 里，早晚有一边漏判。
红线
  • 不要说「我们限制了最大轮数」。轮数上限是最粗的那种控制，说出来会显得你只碰过配置项。
Q6.3Prompt Engineering 和 Context Engineering，你两个都写了，它们不是一回事吧？›
他在测什么

这两个词被混用得最厉害。能一句话切开的人，通常是真的踩过「改措辞没用」的坑。

照着说
「一句话切开：前者改『怎么说』，后者改『给它看什么』。」
「展开一下：Prompt 是措辞、格式、示例、输出契约；Context 是这一轮要装哪几块状态、按什么顺序排、哪块可能缺、哪块已经过期。」
「判断是：改措辞能解决的是表达问题，改上下文才能解决的是信息问题。所以排查顺序永远是——先看信息有没有到达，再改措辞。」
「项目落点：十段有序装配是 context engineering；而『用户说「这个」「这只」时，指上面那个标的』那一句是 prompt engineering——它在教模型怎么读上下文，正好是交界处。」
这是什么

对应技能栏：Agent 应用开发 · Prompt / Context Engineering

同一个症状（答得不对），两种病因：它不知道，还是它不会说。

「不知道」只能靠改上下文；「不会说」才轮到改措辞。反过来做，就是在一件信息没到位的事上，反复雕琢说法。

他要追的话
  • 「那 few-shot 算什么？」算 prompt。但如果示例是从真实运行记录里挑出来的、带来源和版本，它就跨到了 context——因为它改变的是「模型看到的事实」，不只是表达方式。
  • 「你怎么知道自己改的是哪一类？」做个判断：把这次改动撤掉，模型是「话说得不一样」还是「知道的事不一样」。前者是 prompt，后者是 context。这个判据比定义好用。
  • 「上下文工程有没有『过度』的时候？」有。塞得越多，注意力越分散，而且每一段都要有人维护。判据是：这一段删掉，模型会不会答错——不会就该删。
红线
  • 不要说「两个差不多，都是调提示词」。说差不多等于承认只会一个。
Q6.4『结构化输出与解析闸门』是什么？模型输出不都是文本吗？›
他在测什么

你有没有被模型的输出坑过。没被坑过的人写不出这个词。

照着说
「模型输出的是文本，但我们要求它按一份固定的格式交作业——摘要、立场、置信度、分章节。闸门就是收作业时的检查：该有的字段有没有、类型对不对、数值有没有越界，比如置信度给了个 1.5。」
「但关键不是检查，是检查不过怎么办。不合格必须失败，不能兜底填个默认值——兜底会让报告看起来完整、其实是编的，这比直接失败危险得多。」
「所以原则就一句：宁可这次没有报告，也不要一份看起来像报告的假报告。」
补充提醒
「模型老是不按格式出，三个手段从轻到重：提示词里连同一个完整示例一起写（多数情况到这一步就够）、用模型自带的格式约束、最后才是重试——重试贵、慢，而且不治根。」
「闸门要分级：整体格式不合格就抛；单个字段越界（比如置信度 1.5）钳一下继续走，不要整轮作废。」
这是什么

对应技能栏：Agent 应用开发 · 结构化输出与解析闸门

模型输出的 JSON 经常带多余的话、字段缺失、类型不对、数值越界——最典型的是置信度给了 1.5，或者该是数组的地方给了一个对象。

闸门就是在程序接手之前，先确认「这份数据能不能用」。它的价值不在校验本身，在「不合格就失败」这个决定——宁可这次没有报告，也不要一份看起来像报告的假报告。

他要追的话
  • 「模型老是不按格式出，怎么办？」三个手段，从轻到重：把 JSON 形状连同一个完整示例写进提示词（多数情况到这一步就够了）；用结构化输出能力做解码约束；最后才是重试。重试是最后手段，因为它贵、慢，而且不解决根因。
  • 「那你怎么测这个闸门？」拿真实跑坏过的输出当用例。这类样本特别值钱——它们是「模型真的会这样犯」的证据，不是想象的。
  • 「闸门抛错之后，这一轮就废了吗？」看情况。结构不合格通常整轮失败；单个字段越界（比如置信度 1.5）是钳制后继续。所以闸门要分级：能修的修，不能修的抛。
红线
  • 不要说「用了 Zod 就没问题」。校验失败之后你怎么处理，才是设计；Zod 只是那个 if。
Q6.5『Agent 记忆分层』分几层？各存什么？›
他在测什么

你有没有把「记忆」当成一个整体的黑盒。分层的人知道各层该存什么、不该存什么。

照着说
「三层。会话内：这一轮对话的历史和滚动摘要。跨会话的用户或客户事实：人工确认过的那些。组织级知识：文档、政策、规范。」
「三层的差别不在存什么，在生命周期、权威性、失效条件。会话是临时的，可以自动写；事实必须人工确认；知识必须版本化。」
「关键判断：三层的正确性条件不同，就不能共用一个存储。混在一起的结果是——三个月前的一句推测，和昨天人工确认的事实，在检索里权重一样。」
「项目落点：客户偏好进独立表，类型上只允许『已确认』，未确认的记忆在代码里根本构造不出来；公司知识走检索，返回带版本、段落位置、内容指纹。」
这是什么

对应技能栏：知识检索与记忆 · Agent 记忆分层

记忆不是「存得越多越聪明」，是「不同来源的话，可信度不一样」。

所以分层分的其实是责任：谁说的、谁确认的、过期了谁负责。这三件事不同，就不能放进同一个池子里比相似度。

他要追的话
  • 「为什么不全塞进向量库？」因为向量库只解决「像不像」，解决不了「是不是权威」「是不是过期」。相似度高不等于可信，这两件事必须分开判断。
  • 「会话摘要算记忆吗？」算，但是最低一级：可以自动生成、可以丢、不需要人类确认。把它和客户事实放同一层，是最常见的架构错误。
  • 「三层之间怎么流转？」只有一条合法方向：会话里反复出现、又被人确认过的，才升级成事实；事实不会自己降回会话。知识层是只读的，谁都不能往里写。
红线
  • 不要说「我们有短期记忆和长期记忆」。这是产品话术，不是架构。
Q6.6『Token 用量与延迟归因』——归因是什么意思？统计和归因差在哪？›
他在测什么

你会不会把「接了监控」当成「做了观测」。这两件事差一整层。

照着说
「一句话切开：统计告诉你花了多少，归因告诉你花在哪。」
「Token 要拆三段：模型调用，输入多长、输出多长；工具调用，调了几次、每次返回多大；编排开销，重试、子 Agent、并发。」
「延迟也要拆四段：模型首字延迟、模型生成时长、工具往返、排队等待。这四段里哪段涨了，处理方式完全不同——首字慢是模型或网络，生成慢是输出太长，工具往返慢是外部服务，排队慢是自己并发不够。」
「项目落点：采集点在真实执行边界，不在外面包一层；属性只放固定白名单里的十几个 key；导出排除客户正文、工具入参和隐藏推理。」
这是什么

对应技能栏：评测与可观测 · Token 用量与延迟归因

统计是记账，归因是查账。

只有总数的时候，你只知道「这个月贵了」；拆开才知道是模型说太长、还是某个外部接口来回太慢。不做归因的团队会去优化模型选型，实际瓶颈可能在某个外部接口上——方向错了，越努力越贵。

他要追的话
  • 「为什么不在请求外面包一层统计？」外面包一层只能看到「这次总共多久」，看不到里面调了几次工具、每次多久、哪次超时。归因必须发生在调用发生的那一层。
  • 「归因的维度是谁定的？」产品定的，而且故意很少——维度一多，每个维度上的样本就不够看趋势。宁可少几个维度，每个都能对上一条处置动作。
红线
  • 不要说「接了 Langfuse 就有了」。那是采集，归因是你设计好的维度。
Q6.7你写了 TypeScript 和 Next.js——在这种 Agent 系统里，它们各管什么？›
他在测什么

你会不会只是「用过这些框架」。能用一句话说清各自职责边界的人不多。

照着说
「分开说：TypeScript 管契约——工具参数形状、事件类型、状态迁移；Node.js 管进程与流——子进程通信、流式推送、队列任务；Next.js 管入口与鉴权——请求进门、服务端验身份、接口同源。」
「一个判断，也是加分点：TS 的价值不在语法，在类型即契约。工具声明、事件协议、状态迁移写错，编译就过不去。CRM 里『专家子运行不能声明写效果』就是写死在类型里的——想让它写数据，编译不过。靠的不是人记得，是编译器不让。」
「落点：运行时是独立子进程，一行一条事件通信；入口层在服务端验身份，不是只解 cookie。」
这是什么

对应技能栏：工程与工具 · TypeScript / Node.js / Next.js

三件事分得很清：TS 管「说不说得通」，Node 管「跑不跑得动」，Next 管「谁能进来」。

「类型即契约」的意思是：把业务规则写进类型里，违反规则的时候编译就失败——规则从文档变成了一道编译错误。

他要追的话
  • 「为什么不用 Python？」生态决定的。这类系统要和前端共享类型、要在 Node 里跑流式和子进程，用 TS 一套走得通；Python 强在数据处理和训练侧，而这两件事我本来就没做——这也是我说自己做的是应用层的原因。
  • 「React 在里面干什么？」渲染状态。但有个细节值得说：界面状态和模型上下文是两回事——界面里有什么，不等于模型能看到什么。工作区那三行是显式传过去的，不是自动同步的。这个区分没想清楚，就会出现「界面显示 A、模型以为 B」。
  • 「类型写死的东西，运行时还要再查一遍吗？」要。类型只在编译期有效，外部输入（模型输出、HTTP 请求）进来时必须再校验一次。两层不是重复：一层防自己写错，一层防外面乱来。
红线
  • 不要说「我熟悉 TypeScript 高级类型」。除非你能当场写一个条件类型出来。
Q6.8多租户隔离为什么放在数据库里，不放在应用层？›
他在测什么

你懂不懂「机制」和「约定」的差别。这是做企业级应用的入门线。

照着说
「因为两层可靠性不一样。应用层得『记得』给每条查询都加上租户条件——靠人写，漏一次就是看到别家的数据，而且那次不会报错，你也不会发现。」
「数据库不一样：它自带一条访问规则（行级安全），设上之后任何查询都得先过它。条件漏了，查出来是空，不会变成别家的数据。请求进来先解析身份、把租户标识带进数据库会话，规则就拿它过滤每一行。应用层负责传对租户，数据库负责传错了也挡住。」
「但有一层不能混：数据库管『这行你能不能看见』，角色管『这个动作你能不能做』。销售看得见这条商机，不代表他能改阶段。一个在库里，一个在应用层，缺一个就有一类越权。」
补充提醒
「以定义者权限执行的函数会绕过这条规则——知道就好，别主动铺开。被问到就说：这类函数得自己在库里按组织再过滤一遍。」
「队列之所以建在库里，是为了让『改业务状态』和『投递任务』落在同一个事务里，不会出现状态改了、任务没投出去。这个跟租户隔离无关，别混在一起讲。」
这是什么

对应技能栏：工程与工具 · PostgreSQL / Supabase RLS

机制和约定的区别：约定是「大家都记得」，机制是「忘了也做不到」。

一个人写的代码可以靠自觉，一个团队写的系统只能靠机制——因为漏掉的那一次不会报错，只会在半年后变成一次数据事故。

他要追的话
  • 「加了策略会不会拖慢查询？」会，每个查询多一层策略判断。所以要看执行计划，复杂策略要配合索引。这是真实代价，不是免费的。
  • 「那应用层还需要校验吗？」需要，但校验的是不同的东西。库里管「能看到哪些行」，应用层管「这个角色能不能做这个动作」——比如销售能不能改商机阶段。两个维度，缺一个就有一类越权。
  • 「策略写错了，怎么发现？」靠测试里「换一个租户去查同一条记录」的用例。这类用例必须存在，因为策略写错的表现是「查得到」，它不会报错。
红线
  • 不要说「我们用了 Supabase 所以安全」。Supabase 是产品，策略是你写的。
Q6.9Redis 和 Docker 在这两个项目里分别解决什么问题？›
他在测什么

你会不会为了堆技术栈往简历上加词。这道题就是在验这个。

照着说
「Redis 不是缓存，是限流计数器；Docker 只在 CRM 自托管那侧，Folio 不用。」
「Redis 的落点是 AI 请求分发的限流：固定窗口，计数加过期。它不缓存业务数据，客户和会话都不走它，事实权威在库。」
「Docker 是 CRM 自托管套件的运行形态，七个容器。工程点在两处：安装和升级必须同一份实现；归属按目录树、不按容器名——每份 clone 目录名都一样，按名字判会把复制品当成同一安装，拿它的配置去重建生产容器。这在服务器上真发生过。」
「一句话：Redis 是计数器不是缓存；Docker 是运行形态。」
补充提醒
「Redis 不可达时，计数退回进程内存：多实例下共享配额就没了，但业务数据不受影响——退化的是计数，不是存储。」
这是什么

对应技能栏：工程与工具 · Redis / Docker

两个词都容易被写成「我会用」，所以要反过来说清它们在这个系统里到底承担什么：

Redis 是计数器（不是缓存），它管的是「一个组织每秒能发多少次」。

Docker 是运行形态（不是部署方式），它保证「装出来的样子」和「升级后的样子」是同一个。

还有一个配套细节值得记：lib/redis-config.ts 先校验配置形状、再构造客户端——因为 URL 和 token 在环境变量里是纯必填字符串，带引号的值、整行粘贴、heredoc 带来的换行三种都能通过，症状却统一是「Redis 没响应」，指向一个其实健在的容器。

他要追的话
  • 「如果没有 Redis，哪个功能会坏？」多实例下 AI 请求的限流会失效。单实例看不出来——退回进程内存照样在限，所以这是只有扩容才暴露的缺口。
  • 「Docker 起多个容器，调试的时候最麻烦的是什么？」网络归属。反向代理在自有 bridge 上时，容器的 label 必须指向代理自己的网络；代理跑在 host 模式时结论反过来，必须用自己建的 bridge——这两个相反的结论都是实测出来的，靠猜一定错一遍。还有一条：内部网上挂着一个无密码的 Redis，所以对外那张代理网必须是另一张。
  • 「Redis 挂了，限流退回内存，会不会放过流量？」会，而且这是刻意的：宁可放过，也不让整条对话链路挂掉。代价是多实例下配额不共享，所以界面和日志要能看到「现在是降级状态」。
红线
  • 不要说「Redis 用来做缓存提高性能」。它在这套系统里根本不缓存业务数据——它算限额。说成缓存，第一个追问就穿。
Q6.10你写了 Claude Code 和 Codex 工作流，具体怎么用的？›
他在测什么

你是「会用 AI 写代码」还是「被 AI 写代码」。这两者在面试官眼里是两个人。

照着说
「先说边界。用它做什么：读陌生代码、生成测试骨架、批量改重复结构、把报错翻译成人话。不用它做什么：决定架构、判断业务正确性、没有验证手段时改核心逻辑。」
「真实用法：读三千行的文件时，先让它生成调用关系图，再自己顺着关键路径读。省的是定位时间，不是理解时间。」
「风险也要说清：它给的东西必须能被验证——编译过、测试过、或者你能指出它在哪个文件哪一行。验证不了的产出等于没产出。」
「Vitest 那条我说清测什么：测契约不测实现——工具声明、事件顺序、状态迁移，这些变了就是 bug；内部函数怎么拆不该被钉死，否则重构一次改一百个测试。」
这是什么

对应技能栏：工程与工具 · Vitest / Claude Code / Codex 工作流

关键区别是谁在判断：你让它找、让它改，但「这个改法对不对」必须你自己能验。

所以「工作流」的核心不是提示词写得多好，是验证手段——编译、测试、能指到行。没有验证手段的时候用它，等于把判断权交出去了。

他要追的话
  • 「用 AI 编程工具，你的代码能力会不会退化？」会退化的是「记忆型」能力——记 API 签名、记样板代码怎么写；不会退化的是「判断型」能力——这个设计对不对、这个错该不该在这里修。而这活儿值钱的恰恰是后面那个。
  • 「那你写过的最有价值的一个测试是什么？」「传了工作区上下文，prompt 里必须出现标的与视图，并且必须含那句指代消解指令；没传，prompt 里不能出现这一段。」它的价值不在断言本身，在于把提示词变成了可以被回归的对象。
  • 「AI 生成的测试，你会直接用吗？」不会。它是候选用例，我要能让它先红一次、再让它绿一次——红不了，说明它没测到东西。
红线
  • 不要说「我全靠 AI 写」，也不要说「我从来不用」。两个极端都不像真的。
Q6.11你写了 Git——实际是怎么用的？›
他在测什么

会不会只是「会 add、commit、push」。这题真正筛的是「有没有和别人在同一个仓库上协作过」。

照着说
「两个场景：自己写代码，和给别人的仓库提改动。」
「自己写的时候一个改动一条分支，改完先自己看一遍 diff 再合，不往主干上堆。因为想回退的时候分支能整条扔掉，堆在主干上就得一条条挑。」
「更主要的是提 PR，24 个都已合入。流程是 fork、拉分支、只改一件事、跟上 上游的最新变动、解冲突，再等 review。最练人的是两点：改动要小，否则维护者不看完；要提前同步上游，不然等你提的时候主干动了，冲突全砸在自己头上。」
这是什么

对应技能栏：工程与工具 · Git

Git 考的从来不是命令，是「你知不知道自己改的东西怎么进主干」。

三条边界：分支隔离（一个改动一条线）、提交粒度（一件事一次提交，方便回退和 review）、同步时机（早同步，冲突小）。

他要追的话
  • 「冲突怎么解？」先看两边为什么改。同一段逻辑就从行为倒推谁对，只是位置或格式变了就按语义合。最怕随便选一边——能编译，逻辑已经错一半。
  • 「rebase 还是 merge？」给别人的仓库按项目要求来，多数开源项目要求 rebase 成一条干净历史；自己项目的集成分支用 merge，保留「什么时候合的」这个事实。差别是历史留不留分叉，不是哪个更高级。
  • 「会直接推主干吗？」不会，多数仓库权限也不允许，得走 PR。
红线
  • 不要说「我会 add、commit、push」。这三条命令证明不了任何协作经验。
Q6.12你写了 React——在这种 Agent 系统里它具体干什么？›
他在测什么

「会写组件」和「知道界面在 Agent 产品里承担什么」是两回事。这题问的是后者。

照着说
「它管两件事：把流式回来的状态画出来，让用户能插手。」
「具体三块：消息列表要跟着模型的字一个个长出来，还不能整块重画，否则长回答会卡；工具调用的过程要看得见，哪个在跑、跑完没有；运行中间用户要能点取消、能插一句话。」
「有个坑我踩过：界面状态和模型上下文是两回事。界面上显示了什么，不等于模型看得到什么。工作区那几行是显式拼进上下文传过去的，不是自动同步——没理清这个，就会出现界面显示 A、模型以为 B。」
这是什么

对应技能栏：工程与工具 · React

这个前端模块就干两件事：渲染流式返回的状态 + 开放用户干预能力，拆成三块：

消息流式打字效果：模型一字一字吐内容，页面逐字追加，不能整个消息块直接重渲染；长回答如果整块重绘，页面会卡顿。

可视化工具调用过程：展示现在在执行哪个工具、运行状态（进行中 / 完成），把 Agent 内部的执行流程暴露给用户看。

运行时可交互：模型还在输出、工具还在跑的时候，用户随时可以取消，也可以中途插话打断。

React 在 Agent 产品里是「显示器加控制面板」，不是业务逻辑的所在地。

状态要分三层：会话记录（落盘的）、流式中的临时状态（内存里的）、界面交互状态（选中了谁、展开了谁）。混在一起，刷新一次就对不上。

他要追的话
  • 「流式时怎么不整页重渲染？」按消息粒度拆组件，增量只更新最后一条；高频变化的文本单独订阅，别带着整个列表重算。
  • 「刷新以后为什么还能看到半截回答？」因为事件带序号、服务端存了历史，重连时按最后收到的序号补。这不是 React 的能力，是协议的能力，界面只是消费方。
  • 「状态放哪儿？」跨页面共享的进全局，单页面交互的留在组件里。全塞进一个全局对象，最后谁都在改它。
红线
  • 不要说「React 就是写界面的」。这句话等于什么都没说。
Q6.13你写了 Vitest——测试写到什么程度算够？›
他在测什么

有没有被「覆盖率」骗过。真正写过测试的人，知道什么样的测试是负债。

照着说
「我测契约，不测实现。」
「契约是对外承诺的那几样：工具声明长什么样、事件按什么顺序来、状态能从哪个迁到哪个。这些变了就是 bug，测试必须红。实现是内部函数怎么拆、循环怎么写——这些改了不该让测试红，否则重构一次要改一百个测试，人就开始把测试关掉了。」
「还有个习惯：新写的测试先让它红一次。红不了，说明它压根没测到东西。这种测试比没有更坏，因为它给你一个『有覆盖』的错觉。」
这是什么

对应技能栏：工程与工具 · Vitest

测试粒度的问题，本质是「你想在什么变化的时候被拦住」。

契约型测试防的是「对外行为变了没人发现」；实现型测试防的是「内部改动没人知道」——而内部本来就该随便改，不需要防。

他要追的话
  • 「怎么判断一条测试测的是契约还是实现？」删掉它，问「产品行为变了吗」。没变就是测实现。
  • 「一个 bug 修完，测试怎么写？」先写一条在旧代码上会失败的，再修。这条测试才证明「这个 bug 不会回来」。
  • 「覆盖率重要吗？」参考，不是目标。实现型测试也能把覆盖率刷到八成，同时让重构寸步难行。
红线
  • 不要说「我们覆盖率 80%」。覆盖率说明不了测的是不是对的东西。
Q6.14『失败降级与部分成功』——一个任务挂了一半，算成功还是失败？›
他在测什么

你脑子里的「成功」是不是只有 0 和 1。真实系统里最常见的是「成了大部分」。

照着说
「算部分成功，而且必须是一个明确的状态，不是含糊的『大概成了』。」
「举个例子：一份报告要取十项数据，新闻那项超时了。不能让整轮失败——估值和财务白跑，用户还得重来。做法是把失败项标成不可用、写进运行清单，报告照出，缺的那块写在明面上。」
「代价是下游都得能处理不完整的报告：引用少一块、结论要标依据不足、界面要提示。这是把复杂度从『重跑一次』转移到『每个消费方都得判完整性』——我觉得值，但这是有意识的选择，不是白捡的。」
这是什么

对应技能栏：可靠性与成本 · 失败降级与部分成功语义

失败不是二值的。「全成功」和「全失败」之间还有「成了大部分」，以及最麻烦的「不知道成没成」。三种都得能表示出来。

他要追的话
  • 「什么时候该整轮失败？」前置条件没满足时。身份没验过、参数根本不对——继续跑只会产出错的东西。
  • 「部分成功的报告，下游怎么用？」按缺的东西分档：缺的是辅助材料，可以出；缺的是核心依据，只能出「资料不足」的结论。
  • 「跟『不知道成没成』怎么区分？」前者知道缺哪块，后者连缺不缺都不知道——后者必须转人工，不能自己判。
红线
  • 不要说「失败了就重试」。重试解决「这次没成」，解决不了「成了一半」。

Q7.1你说工具调用要过好几道关，能按顺序说一遍吗？顺序能换吗？›
他在测什么

你是记住了「有几道关」还是想清楚了「为什么是这个顺序」。前者一问顺序就崩。

照着说
「六道，顺序不能换。三处换了出事：清洗在验身份前，收窄在执行前，审计前后各一次。」
「按顺序：一，选工具——按白名单筛，分类不明的直接不暴露；二，洗参数——把表示『不知道』的哨兵值清掉；三，验身份——查这次调用要的权限和这个人的角色；四，收窄范围——看碰的东西在不在本次运行的客户范围内；五，执行并审计——前后各记一条；六，把结果包成模型能读的样子。」
「三处理由：清洗在前，否则脏参数带去查库会查出一个不存在的对象，报错还指向权限；收窄在前，查完再判越权等于已经读到数据；审计前后各一次，只记事后再查不出耗时，只记事前查不出成败。」
这是什么

对应技能栏：Agent 应用开发 · MCP 工具契约 + 可靠性与成本 · 副作用分类

这条链的顺序不是拍脑袋，是「越早拦越便宜」：能在一开始就否掉的调用，不要让它走到真正读数据那一步。

把它当安检流程看：先看证件格式对不对（清洗），再看你有没有权限（验身份），再确认这东西能不能带上飞机（收窄范围），最后才过机器（执行），前后都留记录（审计）。

他要追的话
  • 「哪一道最容易漏？」审计。因为它是「没有也能跑」的那一道，最容易在赶进度时被跳过——而它恰恰是出事之后唯一能定位的东西。
  • 「六道关里，哪一道成本最高？」第三道，验身份。它要查权限范围和组织角色，通常是两次数据库查询；其余五道基本是内存判断。所以顺序上把它放在清洗之后，能省掉一批无谓查询。
红线
  • 不要说「都做了」。要能按顺序说出来，并说清换顺序会坏在哪。
Q7.2上下文装配和评测，一个管喂、一个管判，它们有什么关系？›
他在测什么

你知不知道很多「模型不行」其实是「没给它」。这是排查能力的分水岭。

照着说
「关系是：评测断言的很多项，前提是上下文里真的有那个信息。上下文漏了一段，评测会把它记成『模型能力问题』，其实是『供给问题』。」
「关键判断：没有上下文断言的评测，会把供给问题误判成能力问题。一旦误判，所有优化方向都会错——你会去换模型、调温度、加重试，而真正该做的是把那段信息拼进去。」
「正确顺序是：先断言『这一轮必须看到哪几段』，再断言『答案对不对』。前者是后者的前提。」
「项目落点：那三条单元测试就是在做前一件事——传了上下文，prompt 里必须出现标的与视图并含指代消解指令；没传，prompt 里不能出现这一段。」
这是什么

对应技能栏：Agent 应用开发 · Context Engineering + 评测与可观测 · 确定性门禁

评测像考试，上下文像教材。教材没发，考砸了不能怪学生。

所以一套成熟的评测，第一层不是判答案，是判「该给的都给了没」。这一层不做，后面所有分数都在替你背锅。

他要追的话
  • 「那怎么区分是没给还是不会用？」做对照：同一道题，一次给全上下文，一次只给一部分，看差异。差异就是供给的影响；两次都错，才是模型或提示词的问题。这个对照做一次，比争论一天有用。
  • 「上下文断言会不会太脆弱？改一句话测试就红？」会，所以只断言必须出现的事实——标的名、视图名、指代消解那句指令，不断言整段措辞。断言要钉住语义，不能钉住文风。
  • 「上下文断言和答案断言，哪个先写？」上下文断言先写。它便宜、稳定，而且它红了就不用往下看；答案断言红了，你还得分清是没给还是不会用。
红线
  • 不要说「评测就是跑个分」。分不对的时候，第一件事是查输入，不是换模型。
Q7.3幂等、副作用分类、人工确认，分开讲都懂，合起来解决什么问题？›
他在测什么

你会不会把三件事当成三个独立的技术点。真正的工程能力在「它们怎么咬合」。

照着说
「三件事各管一段：副作用分类决定这个动作能不能自动做；人工确认决定谁在什么时候点头；幂等决定点头之后重试几次都不会做两遍。」
「三者缺一，另外两个就白做。有幂等没分类，只读查询也要人点，没人受得了；有分类没幂等，批准后网络抖一下就发两条；有幂等有分类但没人确认，模型判断错时没人拦。」
「合起来保证的不是『一定成功』，是『不会悄悄成功两次』。前者做不到，后者做得到，而后者才是业务真正怕的。」
「项目落点：只有客户信息更新能自动执行，对客消息进待确认；执行时带版本号，副作用前校验租约，状态不确定就不重放、改走人工核对。」
这是什么

对应技能栏：可靠性与成本 · 副作用分类与人工确认 + 队列租约与幂等重试

三件事像三道闸：这道口子允不允许自动过（分类）、谁来按开关（确认）、按两次会不会出事（幂等）。

单独看都是常识，合起来才是一条完整的「不可逆动作」处理流程。缺任何一道，风险就从那道缺口漏出去。

他要追的话
  • 「那不可逆的动作怎么保证？」保证不了「一定成功」，只能保证「不会重复」。所以不可逆动作要么加人工确认，要么加事后对账。「不可逆 + 自动执行」这个组合就不该出现在设计里。
  • 「状态不确定为什么不能重试？」因为不知道上一次到底做没做。重试可能造成第二次；不重试可能漏掉。正确做法是去查副作用应该留下的痕迹，有就补状态，没有才重试——这就是「不确定就不做」。
  • 「三者里哪个最容易在赶工期时被砍？」人工确认。因为它不写代码也能「先上线试试」，而幂等和分类是代码里的结构，砍起来更疼。可砍它等于把误判直接送到客户面前。
红线
  • 不要说「加了唯一索引就幂等」。唯一索引防重复插入，防不住重复的对外动作。
Q7.4RAG、溯源、评测，这三样加起来能不能保证答案里每个事实都对？›
他在测什么

你会不会把「可核查」说成「正确」。这是最容易说过头的一题。

照着说
「不能。但这三件合起来，能保证三件更弱、也更有用的事。」
「一，引用指向的片段真实存在：每条片段带版本、位置、内容指纹，引用能落回具体一段。二，片段确实被检索到过：评测先核对来源标识，防止模型引用一个它根本没见过的东西。三，片段属于当时那个版本。」
「关键判断：这三件合起来是『可核查』，不是『正确』。剩下的部分只能靠人工和语义评审（——把这句话主动说出来，比声称防住了强得多。）」
这是什么

对应技能栏：知识检索与记忆 · RAG / 来源溯源与版本核对 + 评测与可观测

打个比方：这三样保证的是「这本书里真有这一页」，不保证「这一页说得对」。

可核查解决的是「你能顺着线索找回去」；正确解决的是「线索指到的东西本身对不对」。后者需要人判断，或者需要更强的语义评审。

他要追的话
  • 「那过期引用怎么办？」这是要承认的缺口。三个标识目前用于证明来源，没有用于阻止过期引用。要做到后者，需要在检索之后、展示之前再做一次版本有效性检查——这一步在当前实现里不是强制的。
  • 「版本 id 能证明这条政策现在有效吗？」不能，而且这两句话特别容易被混。版本 id 是「被观察的索引的身份」，不是「对这条政策的批准」。
  • 「那要真正做到『每个事实都对』，还缺什么？」缺三样：逐句事实核验（现在没有）、版本有效性检查（现在不是强制）、一个能判「这句话说得对不对」的评审。三样都不便宜。
红线
  • 不要说「有溯源所以不会编」。溯源防的是「查不到」，不是「编得对」。
Q7.5你项目里控成本的地方好像有三处，它们分工是什么？›
他在测什么

你是在「省钱」还是在「控成本」。前者是一句口号，后者是一组分工明确的机制。

照着说
「三个不同的量，各管一段。」
「上下文装配管『一次请求带多少内容』，失控就是单次请求变贵变慢、注意力被稀释。预算门禁管『这个组织这个月能花多少』，失控就是月底对账才发现超支、钱已经花完了。工具额度管『一次任务能调多少次工具』，失控就是某一个任务把整月预算吃光。」
「关键判断：三个的失效方式不同，所以不能用一个开关解决。上下文失控是每次都多花一点，预算失控是总量爆掉，额度失控是局部吃光全局。」
这是什么

对应技能栏：可靠性与成本 · 预算门禁 + Agent 应用开发 · Context Engineering

控制点管的是哪个量失控会长什么样
上下文装配一次请求带多少内容单次请求变贵、变慢、注意力被稀释
预算门禁这个组织这个月能花多少月底对账才发现超支，已经花完了
工具额度一次任务能调多少次工具某一个任务把整月预算吃光

一句话理解：一个管单次、一个管总量、一个管单任务。 三种漏法，所以三个阀门。

他要追的话
  • 「如果只能留一个？」留预算门禁。因为另外两个失控最多让一次任务变贵，预算失控是整月不能用——这是体验问题和业务停摆的区别。
  • 「那超支之后应该重试还是取消？」取消，不重试。用「终止型错误」这个标记告诉队列：这是永久性业务否决，不是系统故障。否则一次超支会变成「N 个会话 × 最大重试次数」次重试，每次一条最高级别告警，把唯一能解释原因的那条淹掉。
  • 「三处里哪一处最容易失效？」工具额度。它是运行时的计数器，最容易在加新路径——比如新增一个子 Agent——的时候忘了共享同一份计数。
红线
  • 不要说「我们做了成本优化」。要说出控的是哪个量，以及不控会怎样。
Q7.6你都有评测了，为什么还要写单元测试？›
他在测什么

分不分得清「代码改坏了」和「模型变差了」。这两件事的失败信号完全不同，混在一起就两头都做不好。

照着说
「它们拦的不是同一种错。」
「单元测试拦代码：参数拼错、状态迁错、边界没处理。跑一次几毫秒，改完立刻知道。评测拦的是模型行为：同一份代码，换个提示词、换个模型版本，回答质量掉了——这个单元测试看不出来，代码没改、测试全绿，答案已经不对了。」
「所以两者顺序是反的：测试保证『我写的东西是对的』，评测保证『它跑出来的东西还是原来那样』。前者便宜，跑在提交时；后者贵，跑在合入前或者夜里。」
这是什么

对应技能栏：工程与工具 · Vitest + 评测与可观测 · 确定性门禁

两类检查回答两个问题：我的代码有没有写错，系统的行为有没有变坏。

单元测试粒度到函数，确定性强、跑得快；评测粒度到一次完整运行，要调模型、要数据集、要判分。前者是开发时的护栏，后者是发布前的闸门。

他要追的话
  • 「评测里不也断言了吗，重复吗？」不重复。评测断言的是「这次运行有没有调到该调的工具、有没有依据」，判运行结果；单元测试判某个函数在给定输入下返回什么。一个在系统边界，一个在函数边界。
  • 「测试能不能代替评测？」不能。模型输出不确定，同一输入两次可能不一样，用测试那套「等于某个值」的断言去卡，一上线红一片。
  • 「评测能不能代替测试？」也不能。评测一次几十秒到几分钟，反馈太慢；而且它只告诉你「这次结果不对」，不告诉你是哪一行错了。
红线
  • 不要说「有评测就不用写测试」。这句话出口，面试官就知道你没维护过测试。
Q7.7你怎么保证合进去的代码、装进容器的镜像、线上跑的是同一份？›
他在测什么

有没有「可追溯」这个概念。出故障时能不能回答「线上这份到底是哪次提交」。

照着说
「靠一条能倒着走的链：线上跑的镜像带标签，标签指到某次提交，那次提交在主干历史里能查到是谁合的。」
「所以要守两件事。构建只从干净的提交来，不能拿本地改了一半的工作区打镜像——否则镜像里的代码在任何地方都找不到。标签不能复用，同一个版本号打两次，出了问题就分不清线上是第一次还是第二次。」
「还有个坑：安装脚本和升级脚本必须共用同一份实现。两边各写一遍，装出来的环境和升上去的环境会悄悄分叉，平时不报错，等出事才发现两边不一样。」
这是什么

对应技能栏：工程与工具 · Git + Docker + 版本化

可追溯不是「有 Git 就行」，是从线上任意一个运行实例，能一路倒推回一行代码。

链条四段：提交 → 构建 → 镜像标签 → 部署记录。任何一段断了，排查就只能靠猜。

他要追的话
  • 「镜像不打标签会怎样？」只能看创建时间，几个人同时构建就分不清谁是谁，每次排查都要重建一次环境去比对。
  • 「升级和安装为什么必须同一份脚本？」它们是同一条路径的两个入口。分开写，一定有一边忘了加某一步——通常是升级那边忘了建某个目录或某个账号。
  • 「回滚怎么回？」回到上一个标签的镜像，而不是「把代码撤回再重新构建」。前者几十秒，后者要重新走一遍构建和验证。
红线
  • 不要说「我们用了容器，所以环境一致」。容器保证运行环境一致，不保证镜像里的代码等于主干上的代码。
Q7.8前端显示的状态和模型看到的状态，怎么保证不打架？›
他在测什么

有没有意识到界面和上下文是两套状态。想不清这点的人，做出来一定出现「界面显示 A、模型以为 B」。

照着说
「先承认一件事：这是两套状态，不是一套。界面有界面的状态，模型有模型的上下文，中间靠一段显式的装配连起来。」
「所以不追求自动同步，追求显式传。用户在看哪个工作区、哪只标的、哪个视图，这几项由前端在每次请求里明确带上去，后端拼进上下文。切标签、改筛选，都不会自动改模型的上下文——必须走一次请求。」
「好处是能解释：模型答错了，可以倒回去看那次请求到底带了什么。坏处是要多写一层，而且容易漏——漏一项，模型就按旧视角回答，界面上一点看不出来。」
这是什么

对应技能栏：工程与工具 · React + Agent 应用开发 · Prompt / Context Engineering

界面状态和模型上下文是两条独立的线，靠「每次请求显式装配」交汇。

不显式传的后果很隐蔽：界面已经切到 B 股票，模型还按 A 回答，而且答得很自信——因为它不知道自己看的是旧视角。

他要追的话
  • 「为什么不干脆让后端读前端的状态？」读不到，也不该读。前端状态在浏览器里，后端每次请求都是独立的；让它去猜，等于把两套状态耦成一团。
  • 「漏传一项怎么发现？」靠评测断言：传了工作区上下文，上下文里就必须出现标的和视图；没传，就不能出现。把「该带什么」写成断言，漏了会红。
  • 「那历史会话呢？」历史是落盘的记录，不是界面状态。三个月后回到这个会话，界面显示当前视角，历史里记的是当时视角——两者本来就不该一致。
红线
  • 不要说「前端状态会自动同步给模型」。没有这种自动，只有显式装配。

Q8.1桌面端为什么用 Electron？主进程和渲染进程怎么分工、怎么通信？›
他在测什么

是不是真做过桌面端。用过 Electron 的人都会说「把网页打包成桌面应用」，但说不清 preload 不是第三个进程、说不清「请求应答」和「事件推送」是两条路，就说明只照着模板搭过壳。

照着说
「Electron 只有两个业务进程：主进程管窗口、内核、落盘；页面那个叫渲染进程。preload 不是第三个进程，它跑在渲染进程里，跟页面隔成两个上下文，把允许调用的方法挂到 window 上。」
「窗口创建时三个开关一起拨：把页面和桥隔开、不许页面直接碰 Node、给渲染进程套沙箱。合起来就一件事：页面拿不到系统能力，只能走桥。」
「通信有两种。页面要结果就走请求应答，invoke 配 handle，回来一个 Promise；主进程要告诉页面有新进展，走事件推送。两条同时跑，invoke 回来不等于这轮跑完，字还在往回推。」
这是什么

对应技能栏：工程与工具 · Electron

三个角色：主进程（握系统能力）、渲染进程（画界面）、preload（渲染进程里的隔离上下文，是唯一的门）。

要记住 sandbox 只针对窗口的渲染进程，主进程本身不在沙箱里。所以真正的防线是「页面拿不到能力」，不是「主进程很安全」——这个区别决定你后面所有校验写在哪。

「分几步」——他要是这么问，就按这个顺序答

建窗口：给 preload 路径，开 contextIsolation、关 nodeIntegration、开 sandbox。

装桥：preload 用 contextBridge 把一份写死的方法清单挂到 window 上，页面只看得见这些名字。

页面调用：页面调 window.electronAPI.xxx()，preload 换成固定通道名，走 ipcRenderer.invoke。

主进程接活：ipcMain.handle 注册的处理器收下，先验参数（该给字符串的给没给、该给对象的给没给），再交给业务层。

回程分两路：业务结果包成统一外壳（成功一种形状、失败一种形状）回给那个 Promise；如果需要过程，另开事件通道推送。

他要追的话
  • 「preload 是不是第三个进程？」不是，它在渲染进程里，只是上下文被隔离。这题答错，等于承认照着模板搭的。
  • 「开了那三个开关就安全了？」不。它挡的是「页面直接调系统能力」，挡不住业务层自己校验不严、也挡不住接口范围开太大。所以参数检查还得自己写，通道名必须写死，不能让页面传任意名字进来。
  • 「为什么不让页面传通道名？」能传就等于页面能喊出任何后端能力，白名单就形同虚设。
  • 「invoke 返回了，这轮是不是结束了？」不是。返回的只是这次请求的结果，Agent 可能还在跑，后续内容走推送。
  • 「页面里能不能直接读文件？」不能。它连 Node 的 API 都没有，只能走桥。
红线
  • 不要说「Electron 就是把网页打包成 exe」。这句话说明你只知道它长什么样，不知道它为什么这么设计。
Q8.2主进程和 Node.js 子进程之间怎么传数据？为什么用 JSONL？›
他在测什么

知不知道跨进程通信里的脏活。JSONL 谁都会说「一行一个 JSON」，但说不清「一次读取可能只拿到半行」，就是没亲手写过。

照着说
「先说要子进程干什么：模型调用会跑很久、会卡住、可能崩。放进独立进程，崩了不至于把整个应用带走。拆进程买的是隔离，付的是多一层翻译。」
「通道用 stdio 三条：标准输入发请求，标准输出收结果，标准错误只放日志。日志混进结果流，解析当场就炸。」
「格式用 JSONL，一行一个 JSON。收的那头先攒够一整行才解析——一次读可能只给你半行，也可能给你三行半，不能假设一次读到一条。」
「所以 JSONL 只是把边界换成了换行，缓冲一点没省。少了缓冲，半行和整行混在一起，出错还往往很晚才发现。」
这是什么

对应技能栏：工程与工具 · Node.js

JSONL 加 stdio 的本质是「一行一封信」：信封之间用换行分隔，所以收信的人必须有缓冲区来对齐信封边界。

这也解释了为什么日志不能写进标准输出——日志不是信封，会污染这条流。

两个错误码值得记住名字：解析失败是 PI_PROTOCOL_ERROR，等太久是 PI_REQUEST_TIMEOUT。面试时能报出名字，比说「有两种错误」重一档。

「分几步」——他要是这么问，就按这个顺序答

起进程：主进程 spawn 子进程，拿到标准输入、标准输出、标准错误三个流。

发请求：对象序列化成一行 JSON 加换行，写进标准输入，带上请求 id。

收数据：标准输出的 data 事件塞进缓冲区，按换行切，切出完整行才解析。

对号入座：按请求 id 找到那个等着回音的请求，把结果还给它。

翻译事件：子进程吐的是它自己的事件名，主进程这一层要翻成自家事件——工具开始、文字增量、消息完成、运行结束。

出错分流：解析失败报协议错，等太久报超时，两个错误码分开。

他要追的话
  • 「为什么不直接用 HTTP 或 WebSocket？」本地两个进程之间不需要网络栈：stdio 没有端口冲突，进程一死流就断，天然能感知到。
  • 「半行怎么办？」留在缓冲区，等下一次 data 事件拼上。绝不能解析一半就判失败。
  • 「背压怎么办？」子进程吐得比消费快，数据会堆在缓冲区里。要么按容量暂停读，要么在协议上做流控。
  • 「一条消息特别大呢？」这就是 JSONL 的边界——单条必须有上限，否则要等很久才凑够一行。
  • 「怎么知道子进程挂了？」标准输出的关闭或退出事件，再加一层请求超时兜底。
红线
  • 只答「一行一个 JSON 所以叫 JSONL」不算答完。这句话证明不了你处理过粘包和半包。
Q8.3Next.js 有几种渲染模式？服务端组件和客户端组件的边界在哪？›
他在测什么

分不分得清「渲染发生在哪」和「代码跑在哪」。会写 Next.js 的人很多，能说清 App Router 下每次请求到底在服务端跑了什么的人不多。

照着说
「渲染分三档：构建时就生成，是静态；每次请求都生成，是服务端渲染；先给静态壳、过一阵再补数据，是增量再生成。App Router 之后还能一页里混着来，靠 Suspense 切开。」
「组件分两类：服务端组件是默认，只在服务端跑，代码不发给前端；客户端组件要标 use client，打包进浏览器，才能用状态和事件。」
「边界我按要不要交互来切：只取数、拼结构就留服务端；要点击、要输入才划到客户端。切反了，不是把数据库连接打进包，就是把交互写死。」
「再往上一层还有 proxy.ts 这道门，身份在那儿验实，后面的模块不用再猜。」
这是什么

对应技能栏：工程与工具 · Next.js

三档渲染解决「快不快」，两类组件解决「代码在哪跑」。两者的共同点是：能在服务端做完的事，不要留到浏览器——既省流量，也不把逻辑暴露出去。

「分几步」——他要是这么问，就按这个顺序答

定渲染：这份数据多久变一次？基本不变——构建时生成；每次都变——请求时生成；隔一阵变——增量再生成。

划组件：默认全部按服务端组件写，只把真正需要交互的那几个标成客户端。

取数：在服务端组件里直接取，不要先发给浏览器、再让浏览器请求一次。

过门：请求进业务之前先过 proxy.ts 那一层，把身份验实，别让后面的模块去猜「这个组织是谁」。

传值：服务端到客户端这道边界上只能传可序列化的数据，函数和实例过不去。

他要追的话
  • 「middleware 怎么改名成 proxy 了？」Next.js 16 的改动：把它定义成应用的网络边界，并且固定在 Node.js 运行时跑，不再有 Edge 和 Node 两套语义。逻辑不变，只改名、改导出函数名。
  • 「getUser 和 getSession 差在哪？」getSession 只解 cookie 里的内容、不做远程校验；getUser 会真去问一次后端。用错了等于把鉴权交给一个可以被伪造的本地缓存。
  • 「服务端组件能用 useState 吗？」不能。它不参与浏览器端渲染，也就没有状态。
  • 「客户端组件能不能直接连数据库？」技术上打得进去，但那等于把连接串和查询语句发给浏览器，绝不该这么做。
  • 「增量再生成会不会给用户看旧数据？」会，这正是它的取舍：用「最多旧 N 秒」换「不用每次都回源」。
红线
  • 不要说「Next.js 就是 React 加了个路由」。这句话说明你没分清渲染发生在哪一侧。

「你们现在评估一个 Agent 改动有没有变坏，是靠人工看还是有一套回归？」
「如果我进来，前三个月你希望我能独立拿下哪一类事？」
这是什么

反问不是走过场，是最后一次展示你想清楚了。

挑问题的原则：问「你们难在哪」，不问「你们是做什么的」（官网有）；问「我进来干什么」，不问「有没有培训」（这个问了显得在挑福利）。

五个可用方向：团队当下的痛点（最推荐）、工程约束、和算法团队的分工、现在在 PoC 还是往生产推、前三个月期望。

  • 不要问薪资、加班、转正比例。这些留给 HR 面。
  • 不要问「公司的主营业务是什么」。官网上有，问了等于没做功课。
  • 不要说「我没有问题了」。这是最没性价比的一句话。

04结尾：真正要背的只有三句›
正文

以上。全篇 79 题，真正需要背下来的只有三句话。

第一句：提示词是意图，注册表是执行——凡是「模型不该做的事」，必须有一条代码拦得住，光写提示词不算。

第二句：依据必须先落盘再综合——报告一旦生成，就必须能对应一组固定的事实，边查边写对不上账。

第三句：缺失要如实保留成「不可用」——漏报是可信度问题，误报是正确性问题，前者更致命。
